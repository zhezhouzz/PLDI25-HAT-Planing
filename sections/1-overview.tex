\section{Motivation}
\label{sec:pret}

We are interested in the generation of test inputs comprised of
sequences of \emph{events} that can be handled by the
system-under-test (SUT); the order of these events in the sequence is
expected to be relevant to the property being checked because of
latent data and control dependencies they exhibit or effectful
behavior they induce.  Examples of applications in which tests are
naturally crafted in this fashion include:
\begin{enumerate}

\item \textbf{Library API invocations:} The SUT is a library
  implementing an effectful abstract data type (ADT) with a set of
  APIs.  A test consists of a sequence of API calls that lead the
  implementation to an error state.

\item \textbf{Serialized inputs:} The SUT is a procedure that processes
  serialized input data, and reconstructs an AST from this input.  The
  inputs produced by the test generator are expected to establish
  semantic dependencies among nodes in the corresponding AST that do
  not satisfy a property of interest.

\item \textbf{Database transactions:} The SUT is a database supporting
  transactional read and write operations under various isolation
  levels.  A test consists of a sequence of transaction operations
  whose interleaved order is chosen to expose violations of isolation
  guarantees by the database.

\item \textbf{Distributed protocols:} The SUT is a distributed system
  whose components are expected to adhere to a protocol.  A test is a
  sequence of message invocations that lead the system to a global
  state in which protocol invariants are not maintained.
\end{enumerate}

\subsection{Type-based Trace Specifications}

We refer to the sequence of events that comprise a test sequence as a
\emph{trace}.  To reason about dependencies among events in a trace
compositionally, we decompose global trace properties into local
specifications assigned as types to individual operations.  We,
therefore, allow type-level specifications to be associated with each
event in a trace, enabling the specification of complex constraints in
a modular fashion, transferring the burden of event quantification and
data dependency management from a trace-level specification language
to a type system.

Concretely, we model these local specifications as a collection of
operation signatures: parameter types constrain the payloads of
events, while the return type captures relationships between
events. We employ symbolic regular expressions (SREs) to qualify
trace-based properties within a type, following prior work on
trace-based type systems~\cite{KT+14,ZYDJ24,NUKT+18}. However, our
formulation generalizes beyond history-sensitive specifications of
effects or state, allowing types to express latent dependencies among
all events, including those that may occur in the future.

Our type abstraction, called a \tyName, has the form
$\uhat{H}{F}$, where the two components
describe the history and future regex (resp.) that establish an underapproximation of behaviours of program execution. Each
signature reads: ``For all trace $\alpha$ that is matched by future regex $F$, there exists a history trace $\alpha_h$ matched by history regex $H$ such that the trace $\alpha$ can be produced by program $e$ under the history trace $\alpha_h$.'' 

\subsection{Examples}

\begin{example}[Set Library]\label{ex:set-library} 
Consider an effectful set library implemented as a fixed-sized array. An incorrect implementation that fails to grow the array when the set is full will result in $\eff{insert}$ operations being dropped. To detect this violation, we need to ascertain whether traces of the following form will raise an exception:
\begin{align*}
  \zevent{insert}{0};\zevent{insert}{4};\zevent{insert}{7};\zevent{delete}{7};\zevent{delete}{4};\textcolor{red}{\zevent{delete}{0} \quad \text{Exception!}}
\end{align*}
\noindent
The implementation uses an underlying array of length $2$, and mistakenly raises an ``element not found'' exception even when element $0$ is supposed to exist. It is expected that all inserted values are unique and the $\eff{delete}$ operation only deletes an element if it was \emph{inserted before and not deleted yet}. These temporal meaning can be expressed using the following trace types:
\begin{align*}
  &\eff{delete} :~ x{:}\Int\sarr \uhat{\allA\msgA{insert}{x}(\anyA \setminus \msgA{insert}{x} \setminus \msgA{delete}{x})^*}{\msgA{delete}{x}}
\end{align*}
\noindent
The signature for $\eff{delete}$ requires that a previous $\eff{insert}$ event occurred and that there is no subsequent $\eff{delete}$ or $\eff{insert}$ event on the same element. This underapproximates the traces to explore, ruling out traces deleting elements that were never inserted (e.g., $\zevent{delete}{3}$) and inefficiently inserting the same value multiple times (e.g., $\zevent{insert}{1};\zevent{insert}{1};\zevent{delete}{1}$). The following code snippet shows a test generator that generates such traces:
\begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
  let rec set_gen (prev_elem: int) =
    () ?$\oplus$?
    let elem = prev_elem + positive_random_int () in
    ?$\eff{insert}$? elem; set_gen (elem); ?$\eff{delete}$? elem
  in set_gen 0
\end{minted}

\noindent The recursive function $\Code{set\_gen}$ consists of two branches combined with the non-deterministic choice operator $\oplus$. It either terminates, or continues to generate nested $\eff{insert}$ and $\eff{delete}$ event pairs on strictly increasing elements.
\end{example}

\begin{example}[Read Atomicity]\label{ex:read-atomicity}
  Database transactions allow concurrent transactions to operate on
  database state.  To mask latency, client-issued read and write
  operations are typically implemented as asynchronous request and
  response event pairs.  It is desirable that read operations be
  logically atomic, i.e., the response to a client-issued read request
  on a key $k$ always returns the last committed value of $k$ \emph{at
    the time of the request}. The following trace captures an
  execution that violates read atomicity\footnote{For simplicity, we assume
    the database manages a single key that is elided
    from event arguments.}; we also assume that
  every $\eff{writeRsp}$ event is also a commit point: {\small
  \begin{align*}
    &\text{\textcolor{gray}{Client 1:}}  & \zevent{writeReq}{\iota_1,4};\zevent{writeRsp}{\iota_1,4};&
    \\& \text{\textcolor{gray}{Client 2:}} \quad \zevent{readReq}{\iota_2,3};\zevent{readRsp}{\iota_2,3};\zevent{readReq}{\iota_2};& &\zevent{readRsp}{\iota_2,4}
  \end{align*}}\noindent
  Here, \textcolor{gray}{Client 2} issues two consecutive read
  operations.  A $\eff{readReq}$ event initiates a request to the
  database with transaction id $\iota_2$; the response from the
  database is subsequently observed by a matching $\eff{readRsp}$ that
  follows the request.  In this trace, however, the second response
  witnesses a committed write performed by another
  concurrently-executing, non-committed transaction, with transaction
  id $\iota_1$, that occurs after the request.  The following
  trace specification on
  $\eff{readReq}$ events admits executions that satisfy read atomicity:
  \begin{align*}
    &\eff{readRsp} :~ \uhat{\Code{LAST}(\msgA{writeRsp}{\iota\;x})\msgA{readReq}{\iota}\allA}{\msgA{readRsp}{\iota\;x}}
  \end{align*}\noindent
  The regex specifies that if a transaction with id $\iota$ last
  observes that the value of the single key managed by the database is $x$ at the point of $\eff{readReq}$ happening,
  then the response value made by the transaction
  must also be $x$, regardless of any intervening operation.
  \Code{LAST}($\eff{evt}$) is an alias for the following regex:
  \begin{align*}
    \Code{LAST}(\eff{evt})   \equiv \allA; \eff{evt}; (\anyA \setminus \eff{evt})^*
  \end{align*}
  Any trace in which a response to a request yields a different
  value than previously seen by the transaction exposes a
  read atomicity violation. 
  
  Our DSL supports \emph{interactive} test generation through the $\mykw{obs}$ syntax, which enables tests to dynamically observe the effects of the SUT and control subsequent generation behavior. For instance, the following test generator for the read atomicity property utilizes $\mykw{obs}$ to inspect SUT responses:
  \begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
    let rec transaction_gen () =
      let x = random_int () in
      ?$\eff{writeReq}$? x; let _ = ?$\mykw{obs}\;\eff{writeRsp}$? in
      ?$\eff{readReq}$?; 
      ?$\eff{writeReq}$? (x + 1); let _ = ?$\mykw{obs}\;\eff{writeRsp}$? in
      let y = ?$\mykw{obs}\;\eff{readRsp}$? in (assert (y != x) ?$\oplus$? transaction_gen ())
  \end{minted}

  \noindent In each iteration, the generator issues two distinct writes (line 3 and 5) with a read request in between (line 4),  and observing the read result $y$ via $\mykw{obs}$ (line 6). It then compares $y$ with $x$ to determine whether to terminate (i.e., the read result is different from the first written value) or recursively generate further transactions.
\end{example}

\begin{example}[Strong Consistency]\label{ex:sc} 
As another concurrency example, we consider how a simple key-value store might respond to a message $\zevent{getReq}{\Code{key}}$ that queries the value of a key $\Code{key}$ under different consistency guarantees.
In any reasonable implementation, the value $\Code{val}$ in a response message $\zevent{getRsp}{\Code{key},\Code{val}}$ should correspond to \emph{some} value the database stored in response to a previous $\eff{putReq}$ request.
We can encode these dependencies via the following \tyName{} for the $\eff{getRsp}$ response:%
\vspace{-.4cm} \par\nobreak {
  \begin{align*}
    \uhat{\allA \msgA{putReq}{\Code{key}\;\Code{val}} \allA \msgA{getRsp}{\Code{key}}\allA}{\msgA{getRsp}{\Code{key}\;\Code{val}}} %
  \end{align*}
}\noindent
Intuitively, this type guides the test generator to produce eventually consistent (EC)~\cite{Burckhardt2014,Session} behavior, since the store is free to buffer and respond to $\eff{put}$ and $\eff{get}$ requests arbitrarily.
While performant, this policy can be too permissive for users, who may expect the store to be strongly consistent (SC), i.e., one that always returns the value of a key as it was at the point a request message is handled.
We can specify a violation of SC using the following \tyName{} for the test generator:
\vspace{-.4cm} \par\nobreak {
  \begin{align*}
    \uhat{\epsilon}{\allA\msgA{putReq}{\Code{key}\;\Code{val}} (\anyA \setminus \msgA{putReq}{\Code{key}})^* \msgB{getRsp}{k\;v}{k = \Code{key} \land v \not= \Code{val}}}
  \end{align*}
}\noindent
Observe that checking whether a store is SC cannot be accomplished by testing how the database handles these messages in isolation: a violation of SC crucially depends on a specific sequence of get and put messages with appropriate inputs.
The above specification identifies an erroneous execution of the SUT as one in which the last $\eff{putReq}$ binds $\Code{key}$ to $\Code{val}$, but a $\eff{getRsp}$ message on $\Code{key}$ generated in response to a previously issued $\eff{getReq}$ message returns a value other than $\Code{val}$.
\end{example}


\begin{example}[Information-Flow Control]\label{ex:ifc} 
As a final example, we consider test generation for a secure information-flow control (IFC) abstract machine that enforces end-to-end noninterference (EENI)~\cite{pbt-ifc}: if two input programs and initial machine states are indistinguishable to a \emph{public observer}, then the resulting final states must also be indistinguishable. We encode the IFC machine input as a sequence of commands, where each command consists of a pair of arguments representing two syntactically aligned but potentially secret-differing programs.
For instance, the following serialized input corresponds to two indistinguishable IFC programs that both store value $1$ from stack into memory, but at different addresses:
\begin{align*}
  &\zevent{push}{\Code{L}, 1, 1};\zevent{push}{\Code{H}, 0, 1};\eff{store} \equiv
  \\\text{\textcolor{gray}{Program 1:}} \quad &\zevent{push}{\Code{L}, 1};\zevent{push}{\Code{H}, 0};\eff{store} \quad \text{\textcolor{gray}{and}} \quad  \text{\textcolor{gray}{Program 2:}} \quad \zevent{push}{\Code{L}, 1};\zevent{push}{\Code{H}, 1};\eff{store} 
\end{align*}\noindent
Here, $\Code{L}$ and $\Code{H}$ are the low (public) and high (secret) security levels, with $\Code{L} \sqsubseteq \Code{H}$.
To ensure indistinguishability, public commands (level $\Code{L}$) must use identical argument values in both programs, whereas secret commands (level $\Code{H}$) may choose different address values ($0$ and $1$).
Random generation of such IFC commands often yields invalid or uninteresting cases, e.g., $\zevent{push}{\Code{L}, 1, 0}$ (violates noninterference), $\zevent{push}{\Code{L}, -1, -1};\eff{store}$ (invalid address), or $\zevent{push}{\Code{H}, 1, 1}$ (uninteresting secret).
To avoid these, we employ the following \tyName{} types to guide generation:
\begin{align*}
  \eff{push} :~& \uhat{\allA}{\msgB{push}{\I{lvl}\;x\;y}{\I{lvl} = \Code{L} \iff x = y}}
  \\\eff{store} :~& \uhat{\allA\msgC{push}\allA\msgB{push}{\I{lvl}\;x\;y}{\I{isAddr}(x) \land \I{isAddr}(y)}}{\eff{store}}
\end{align*}\noindent  
The type of $\eff{push}$ enforces that the arguments are equal only at the public level, while the type of $\eff{store}$ ensures that the value to store exists (i.e., $\allA\msgC{push}\allA$) and that it is preceded by a $\eff{push}$ with valid addresses.
\end{example}
