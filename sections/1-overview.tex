\section{Overview}
\label{sec:overview}

To motivate our approach, consider how we might test the (highly
simplified) model of a distributed database application depicted in
\autoref{fig:database}.

\begin{figure}[t!]
    \centering
    \includegraphics[width=0.75\linewidth]{figures/Controller-Database.drawio.png}
    \caption{A simplified database access workflow.}
    \label{fig:database}
\end{figure}

This system includes two components: a user that issues read and write
messages to a model of a database under test, and a database component
responsible for persisting user-supplied writes, and responding to
user requests to read its contents.  To simplify this example, we
assume the database manages a single integer-valued record that users
can read and write.  As with the earlier key-value store, messages are
asynchronous and separated into two categories, one for requests and
another for the corresponding responses.  Each response carries a
status flag indicating if the request was successful.  A \textsf{true}
status value on a $\eff{writeRsp}$ message indicates that the
corresponding request was successfully persisted to the database,
while a \textsf{true} status flag on a $\eff{readRsp}$ message
indicates that the database is not empty, and the integer in its
payload corresponds to a previously written value.

Since our focus is on deriving a controller that schedules messages
and determines payloads to drive a testing procedure, we are
unconcerned with the implementation of the database --- our primary
interest is in the specification of its interface and the dependencies
that must hold on messages sent between the users and the database,
since these are the primary elements that inform scheduling decisions.
Our goal is to synthesize a controller that generates user requests
and orders the delivery of messages between the user and the database
in a way that drives executions towards a violation of a desired
safety property.

In the figure, the $\eff{readReq}$ and $\eff{writeReq}$ messages sent
by the user are independent of any prior messages and any actions
taken by other components, and can then thus be freely created and
sent by a controller. We refer to such messages as
\emph{generable}. In contrast, messages sent from the database back to
to the user are can only be produced in response to other message. As
the controller can only indirectly trigger such messages, we refer to
them as \emph{observable}.

\paragraph{Traces and safety}
In response to user inputs, an executable model generates a sequence
of messages with concrete values as payloads, which we refer to as a
\emph{trace}.  For our running example, we assume a user expects the
database to satisfy a \emph{read-your-writes} (RYW) policy~\cite{...}
in which reads should see the most recent write to the database.
Under a database that provides EC semantics, however, users might
witness the following trace: %
{\small
  \begin{align}
    &\effGreen{writeReq(3)};\effBlue{writeReq(4)};\effBlue{writeRsp(4,\true)};\effRed{readReq};\effGreen{writeRsp(3,\true)};\effRed{readRsp(4,\true)}
      \label{eqn:traceEx}\tag{$tr_1$}
  \end{align}}
\noindent In this trace, the $\effRed{readRsp}$ message is generated
in response to a previously issued $\eff{readReq}$, but returns a
value other than the most recently written one.  This can happen, for
example, when messages on $\eff{writeReq}$ events are not guaranteed
to be serviced in-order, or when the database state is replicated and
the effect of the $\effGreen{writeRsp(3,true)}$ event has not been
propagated to the replica that responds to the $\effRed{readReq}$
message.

The following symbolic LTL$_f$ formula~\cite{...}: formally captures a
violation of RYW: %
{\footnotesize
  \begin{align} \finalA (\msg{writeRsp}{v = \Code{x} \land st = \true}
    \land \nextA (\neg \msg{writeRsp}{st = \true} \untilA
    \msg{readRsp}{v = \Code{y} \land st = \true \land \Code{y} \not=
      \Code{x}})
    \label{eqn:autoEx}\tag{$\negSCA$}
  \end{align}} %
\noindent
Here, $\msg{writeRsp}{v = \Code{x} \land st = \true}$ is a predicate
on messages, referred to a \emph{symbolic event}. This predicate
stipulates that this is a succesful $\eff{writeRsp}$ message that
reports the value $\Code{x}$ was written. The formula reads as: "this
trace \emph{eventually} includes a $\eff{writeRsp}$ message reporting
$\Code{x}$ was successfully written; moreover, there are no further
successful writes \emph{until} an $\eff{readRsp}$ message with a
payload $\Code{y}$ different from $\Code{x}$ appears."  This formula
can be translated into a Symbolic Finite Automata (SFA)~\cite{...}, on
which inclusion and emptiness are decidable. It is important to note
that this specification defines an \emph{overapproximation} of
violating traces: not all traces that satisfy this property will be
produced by our database model. For example, although the trace
$\effGreen{writeRsp(3,\true)};\effBlue{readRsp(-1,\true)}$ satisfies
\ref{eqn:autoEx}, it does not correspond to a valid execution of our
model, as it does not contain request messages for either responses.

\paragraph{Controllers}
As mentioned earlier, testing a reactive distributed system requires
the support of a controller that models the environment in which it is
run.  We introduce a DSL for writing such controllers amenable to
automated synthesis. A controller program manages the generation of
messages, schedules message order, and constrains data dependencies
between messages.  Concretely, to realize the trace \ref{eqn:traceEx},
the controller must (a) issue user-generable messages (e.g.,
$\effGreen{writeReq(3)}$), and (b) ensure that
$\effGreen{writeRsp(3,true)}$ message is allowed to be delivered
before $\effRed{readRsp(4,\true)}$.

A controller program $P_{C}$ that generates traces sufficient to
violate $\negSCA$ is shown in \autoref{fig:2pc-term}. The program
stipulates an ordering on messages which are tagged by the keywords
$\mykw{gen}$ and $\mykw{obs}$ to indicate whether the message is
generated by the user or the database (i.e., the system-under-test).
The program also provides the payloads for generable messages, and it
binds the payloads of observable messages to new variables using
\lstinline|let|. The constraints on parameters $\Code{x}$ and
$\Code{y}$ are defined by the $\mykw{assert}$ statements on line 1.
Importantly, since the controller does not control the behavior of
internal components, it cannot mandate the specific values output by
the database in response to a message. Instead, it uses assertions to
prune executions that will not satisfy $\negSCA$. Our synthesis
algorithm adds these assertions to a controller using the
specifications of component.  Consequently, assertions may fail; for
instance, if the database component sends a $\eff{writeRsp}$ message
with a $\false$ status, this would violate the assertion on line 4.
Nonetheless, our synthesis procedure guarantees that it will generate
an execution of the system that produces the expected traces in
$\negSCA$, if one exists.

\subsection{Prophecy Automata Types}

In the absence of any assumptions about component behaviors, all
traces are worth exploring to see if they witness a violation (e.g.,
$\negSCA$), including clearly incorrect traces such as
$\effGreen{writeRsp(3,\true)};\effBlue{readRsp(-1,\true)}$, as noted
previously.  To filter out these unrealizable traces, we need
specifications for components that establish necessary message
dependencies that any sensible trace should respect.  Our
specifications are both temporal (e.g., response messages should
follow corresponding request messages) and data-dependent (e.g., the
payload of a read response should match the most recent write
value). On the other hand, they should also align with the actual
implementation of system under test. Unlike defining a violation
property, crafting an s-LTL$_f$ property $\specRealizable$ to
precisely capture all feasible traces is non-trivial, as different
messages are handled by different components.

To achieve both expressiveness and compositionality, we introduce a
trace-based refinement types \cite{...} to constrain the behavior of a
component's message handlers, instead of providing a global
specification that characterizes the entire distributed state. In our
approach, component behavior is modeled as a set of function types,
where each function name corresponds to a message name, parameter
types define constraints on message payloads, and return types specify
relationships between messages.  Unlike prior work that incorporate
trace-based types, our model incorporates asynchronous semantics,
where handling one message can trigger the sending of new messages
that will only be received later.  Intuitively, this means that the
return type of a handler must include both a ``rely", specifying
assumptions about prior events that allow this type to be manifested,
and a ``guarantee" that constrains future events. Based on this
intuition, we introduce Prophecy Automata Types (\PAT), which provide
constraints on traces that regulate the kind and content of messages
that are received after the handler returns.

\paragraph{History, current, and prophecy automata}   Handler
specifications for our motivating example is shown in
\autoref{fig:spec}. The return type of an event has the form
$\rg{H}{A}{F}$, where $H$, $A$, and $F$ represent the history,
current, and prophecy automata, resp. that establishes the context and
effect for any message over this event.  Recall that a \PAT\ type
reads: ``If a program is executed under a context trace accepted by
the history automaton $H$, then the effect of executing this program
is defined by the current automaton $A$; moreover, the future trace
(i.e., the remaining part of the execution) will be accepted by the
prophecy automaton $F$''. Intuitively, prophecy automata serves as the
trace-based analogue of prophecy variables\cite{...}, which have been
introduced in other state-based concurrency reasoning approaches. For
example, the first type in \autoref{fig:spec} characterizes the
behavior of $\eff{writeReq}$ messages.  Its history automaton allows a
$\eff{writeReq}$ to be handled in any context
($\globalA\evparenth{\top}$).  The current automaton admits a trace
with a single message, specified by the $\lastA$ modality, namely
$\eff{writeReq}$ itself.  More interestingly, the prophecy automaton
guarantees that, given a trace that satisfies $H$ and $A$, a
$\eff{writeRsp}$ message will be handled in the future, as specified
by the $\finalA$ modality.  This specification captures the
asynchronous behavior of request/response pairs in our example,
requiring that the handler of $\eff{writeReq}$ eventually trigger a
$\eff{writeRsp}$ message.

\paragraph{Control flow} The history, current, and prophecy
automata can also describe salient control-flow of the message
handler. For example, the type of $\eff{readReq}$ makes use of
intersection types ($\interty$) to encode the two situations the
handler may face in responding to this request, namely whether a value
has been previously written to the database or not. The first type
indicates that the handler should send the last written value,
as specified in the history automata
{\footnotesize\begin{align*}
 \finalA \msg{writeReq}{v = \Code{x}} \land \neg\nextA\finalA\msg{writeReq}{\top}\end{align*}}\noindent
as a response message ($\msg{readRsp}{v = \Code{x} \land st}$) with
$\true$ status, as specified in the prophecy automata.  Otherwise,
there is no write value ($\neg\finalA \msg{writeRsp}{\top}$), and a
$\eff{readRsp}$ message with a $\false$ status should should
eventually be returned ($\finalA\msg{readRsp}{ \neg st}$). On the
other hand, the handlers of observable messages $\eff{readRsp}$ and
$\eff{writeRsp}$ are unconstrained by the controller. Thus, the
prophecy automata of these types cannot make any guarantee about
future ($\allTL$) actions, since we have no control over how they
can generate subsequent messages in response to previously issued
ones.

\paragraph{Typechecking} By defining message behavior
in terms of \PAT\ type specifications, we can perform standard
refinement type checking on controller programs to decide if they are
consistent with specification constraints. In this sense, we can treat
$\mykw{gen}$ and $\mykw{obs}$ terms in the controller program as as a
form of function application that should be consistent with the
specification of the corresponding handler.

For example, to check that the controller $P_{C}$ is type-safe, an observed
$\eff{readReq}$ term on line $5$ in \autoref{fig:spec} ``divides'' a
program execution into three pieces: a history (line $1$ - $4$), an
action (line $5$), and a future (line $6$ - $7$). These three pieces
are consistent with the type specification for $\eff{readReq}$, which
requires the last value written to the database is $\Code{y}$ (line
$3$) in the history, that the message being handled is
$\eff{readReq}$, and that there will be a future $\eff{readReq}$
message with value $\Code{y}$ produced in the future (line
$7$). Notably, $P_{C}$ can indeed induce a trace that violates an RYW
consistency policy. This can be shown by typechecking it against a
context specified by the \PAT\ type
$\rg{\globalA\evparenth{\bot}}{\negSCA}{\globalA\evparenth{\bot}}$,
that assumes there is no history message,
($\globalA\evparenth{\bot}$), the execution of the controller
generates a trace consistent with $\negSCA$, and there are no more
messages to be received in the future ($\globalA\evparenth{\bot}$).

By treating messages as invocations of component handlers, we can
formulate a type-guided, component-based synthesis problem, where the
types of component methods are provided as handler specifications, as
shown in~\autoref{fig:spec}. Because na\"{\i}ve enumeration of
these message invocations is impractical, our synthesis procedure
instead incrementally refines the violation property to increase the
number of infeasible or unrealizable traces that should not be
considered.  As illustrated in \autoref{fig:intuition-algo}, our
algorithm consists of two parts. First, it systematically refines the
given property $A$ that we are interested in violating to a stronger
property $A'$, where $A' \impl A$, ensuring that all message
invocations in $A'$ align with provided specifications. Second, it derives a
corresponding controller program from $A'$. For instance, the set of
traces denoted by $\negSCA$ can be refined into:
{\footnotesize\begin{align*}
  \negSCA'
  \doteq &\msg{writeReq}{v = \Code{x}} \seqA \msg{writeReq}{v =
    \Code{y} \land v \not= \Code{x}} \seqA \msg{readReq}{\top} \seqA
  \\&\msg{writeRsp}{v = \Code{y} \land st = \true} \seqA
  \textcolor{DeepGreen}{\msg{writeRsp}{v = \Code{x} \land st = \true}} \seqA
  \textcolor{red}{\msg{readRsp}{v = \Code{y} \land st = \true \land v \not=
      \Code{x}}}
\end{align*}}\noindent
This trace specializes the set of messages admitted by the s-LTL$_f$
formula enclosed within the $\finalA$ modality in $\negSCA$ with
specific instances of $\eff{writeReq}$ and $\eff{readReq}$ messages.
To highlight that all traces consistent with $\negSCA'$ also satisfy
$\negSCA$, we highlight two key symbolic events, $\effGreen{writeRsp}$
and $\effRed{readRsp}$, which violate the RYW consistency policy.  As
shown, the property $\negSCA'$ closely resembles the controller
program $P_{C}$. The main difference is that $P_{C}$ is more
operational, dividing messages into $\mykw{gen}$ (generable) and
$\mykw{obs}$ (observable) groups. The controller also provides
payloads for $\mykw{gen}$ messages, while payloads in $\mykw{obs}$
messages are constrained only by local variables.

\paragraph{Property Refinement Loop}
The property refinement process is crucial, as it adapts
\PAT\ specifications to constrain all messages in the refined property
$\negSCA'$. Although $\negSCA'$ includes six events, not all (e.g.,
$\eff{readReq}$) are directly found in the original, $\negSCA$. The
algorithm dynamically adds new messages that need to be checked as
synthesis proceeds.  Viewed from another perspective, our approach
functions as a trace-exploration algorithm, searching for traces that
witness a property violation until one is found that aligns with
provided specifications. The primary challenge lies in handling
temporal modalities like $\finalA$ and $\untilA$ that admit an
arbitrary number of possible messages in the trace before the messages
of interest occur.  To address this, our synthesis procedure injects
new messages in the controller program lazily.  For example, when
checking the type of the $\eff{readRsp}$ message, the last message in
$\negSCA$, the algorithm identifies that it is issued by the handler
for $\eff{readReq}$ (via the first case in the intersection type that
defines $\eff{readReq}$). Moreover, $\eff{readReq}$'s type also
indicates that the message payload $\Code{y}$ should belong to a
previous $\eff{writeReq}$.  Based on these constraints, it then adds
$\eff{writeReq}$ and $\eff{readReq}$ messages before $\eff{readRsp}$
in the refined property, also marking them as messages whose
constraints must subsequently also need to be satisfied, ultimately
leading to the refined property.
