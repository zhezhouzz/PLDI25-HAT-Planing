\section{Overview}\label{sec:overview}


We propose a trace-based type-guided synthesis framework for
generating effectful input test sequences in a PBT system interacting
with a SUT comprised of opaque, potentially concurrent and/or
distributed, components.  Before present the synthesis algorithm, we
first present the key features of our approach, followed by
illustrative examples from multiple domains.

\subsection{Trace-based Specifications}

The inputs and observed outputs of an effectful operation (e.g.,
$\eff{put}$ or $\eff{get}$ in our earlier example) is recorded as an
\emph{event} in a \emph{trace}, which is simply a sequence
of events.  To reason about dependencies among events in a trace
compositionally, we decompose global trace properties into local
specifications assigned as types to individual operations.  We,
therefore, allow type-level specifications to be associated with each
event in a trace, enabling the specification of complex constraints in
a modular fashion, transferring the burden of event quantification and
data dependency management from a trace-level specification language
to a type system.

Concretely, we model these local specifications as a collection of
operation signatures: parameter types constrain the payloads of
events, while the return type captures relationships between
events. We employ symbolic regular expressions (SREs) to qualify
trace-based properties within a type, following prior work on
trace-based type systems~\cite{KT+14,ZYDJ24,NUKT+18}. However, our
formulation generalizes beyond history-sensitive specifications of
effects or state, allowing types to express latent dependencies among
all events, including those that may occur in the future.

\subsection{The \name\ DSL}

To support test generation across diverse domains, we introduce a
domain-specific language (DSL) based on the lambda calculus, extended
with recursion, nondeterministic choice ($\oplus$), and (asynchronous)
effectful operations ($\eff{op}$), to serve as a basis for writing
(and, in our case, synthesizing input test sequences.  As we show
below, asynchronous events allow traces to treat the initiation of an
effect by the SUT (modeled as a \emph{request} event) separately from
its completion (modeled as a \emph{response} event).  The DSL enables
asynchronous interaction with the SUT through the $\mykw{gen}$ and
$\mykw{obs}$ primitives, the former being used to initiate an effect
and the latter used to observe its result.  For example,
$\sgen{ReadReq}{}$ asynchronously generates a read request to the SUT,
whose result can be subsequently observed via an
$\zobs{x}{readRsp}{\!\!}{e}$ event, that binds the result of the read
operation to to $x$ in the $\mykw{let}$-body $e$. This style of trace
generation enables concise expression of interactive test generators
for systems such as database transactions and distributed protocols
that are inherently concurrent.  The DSL further allows random value
generation and property checking via $\mykw{assume}$ and
$\mykw{assert}$ operations. Concretely, an $\mykw{assume}(\phi)$ event
constrains $x$ in the trace follows to random values that satisfy the
assumption $\phi$, while $\mykw{assert}(\phi)$ allows further
processing of a trace only if formula $\phi$ holds.

\begin{example}[Read Atomicity]\label{ex:read-atomicity}
  Database transactions allow concurrent transactions to operate on
  database state.  To mask latency, client-issued read and write
  operations are typically implemented as asynchronous request and
  response event pairs.  It is desirable that read operations be
  logically atomic, i.e., the response to a client-issued read request
  on a key $k$ always returns the last committed value of $k$ \emph{at
    the time of the request}, regardless of writes that may have been
  committed between the request and response. The following trace captures an
  execution that violates read atomicity\footnote{For simplicity, we
    assume the database manages a single key that is elided from event
    arguments.}; we also assume that every $\eff{writeRsp}$ event is
  also a commit point that makes the value written available to
  subsequent $\eff{readReq}$ events: {\small
  \begin{align*}
    &\text{\textcolor{gray}{Client 1:}} \zevent{writeResp}{3} & \zevent{writeReq}{4};\zevent{writeRsp}{4};&
    \\& \text{\textcolor{gray}{Client 2:}} \quad \quad \quad \quad \quad \quad \zevent{readReq}{};\zevent{readRsp}{3};\zevent{readReq}{};& &\textcolor{red}{\zevent{readRsp}{4}}
  \end{align*}}\noindent
  Here, \textcolor{gray}{Client 2} issues two consecutive read
  operations.  A $\eff{readReq}$ event initiates a request to the
  database; the response from the database is subsequently observed by
  a matching $\eff{readRsp}$ that follows the request.  In this trace,
  however, the second response witnesses a write committed by another
  concurrently-executing transaction that occurs after the request.
  We are interested in surfacing executions like these from \tyName{}
  specifications.  The following \tyName{} type on
  $\eff{readReq}$ events admits executions that satisfy read
  atomicity:
  \begin{align*}
    &\effLR{\Code{LAST}(\msgA{writeRsp}{v})\Code{LAST}\msgA{readReq}{}}\; \zobs{x}{readRsp}{e}\; \effLR{\msgA{readRsp}{v}}
  \end{align*}\noindent
  This type specifies that if the SUT responsed to a previously issued
  $\eff{readReq}$ with value $v$, then the last committed write prior
  to the request must have written $v$.  Note that because this
  specification is interpreted as an underapproximation of the
  possible behaviors of the SUT, it establishes a clear dependence
  between $\eff{writeRsp}$ and $\eff{readReq}$, and $\eff{readReq}$
  and $\eff{readRsp}$ events - every trace sequence that satisfies
  this specification must respect this dependence.  The specification
  uses \Code{LAST}($\eff{evt}$) as an alias for the following regex:
  \begin{align*}
    \Code{LAST}(\eff{evt})   \equiv \allA; \eff{evt}; (\anyA \setminus \eff{evt})^*
  \end{align*}
  Thus, any trace that does not satisfy this type, i.e, a trace in
  which a response to a request yields a different value than
  previously seen by the transaction, exposes a read atomicity
  violation.
  
  As mentioned above, our DSL supports \emph{interactive} test
  generation through the $\mykw{obs}$ syntax, which enables tests to
  dynamically observe the effects of the SUT and control subsequent
  generation behavior. For instance, the following test generator is
  automatically synthesized from the above specification
  utilizes $\mykw{obs}$ to inspect SUT responses:
  \begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
    let rec transaction_gen () =
      let x = int_gen () in
      ?$\eff{writeReq}$? x; let _ = ?$\mykw{obs}\;\eff{writeRsp}$? in
      ?$\eff{readReq}$? ; 
      ?$\eff{writeReq}$? (x + 1); let _ = ?$\mykw{obs}\;\eff{writeRsp}$? in
      let y = ?$\mykw{obs}\;\eff{readRsp}$? in assert x == y; (() ?$\oplus$? transaction_gen ())
  \end{minted}
  \noindent In each iteration, the generator issues two distinct
  writes (lines 3 and 5) with a read request in between (line 4), and
  observes the read result $y$ via $\mykw{obs}$ (line 6). Before
  generating further transactions, it compares $y$ with $x$ to
  determine whether to terminate the generation of additional tests
  and report a violation (i.e., if the read result is different from
  the first written value).
\end{example}

\begin{example}[Information-Flow Control]\label{ex:ifc} 
~\cite{pbt-ifc} considers a PBT formulation for a secure
  information-flow control (IFC) abstract machine that enforces
  end-to-end noninterference (EENI).  This property captures the
  notion that secret inputs should not influence public ouputs: any
  two executions starting from the same initial state that are
  indistinguishable (i.e., pairs of executions where all ``low''
  security values are the same) should end in terminating states that
  are also indistinguishable.  The methodology adopted
  in~\cite{pbt-ifc} encodes the IFC machine input as a sequence of
  stack machine commands.  For instance, the following serialized
  input corresponds to two IFC programs that both store value $1$ from
  stack into memory, but at different addresses; the only difference
  is the pointer address which is labeled \textsf{H} and thus not
  visible to an observer:
  \begin{flalign*}
   & \quad \quad \quad \quad  \zevent{push}{\Code{L}, \langle 1, 1\rangle};\zevent{push}{\Code{H}, \langle 0, 1\rangle};\eff{store} \equiv
  \\
  \text{\textcolor{gray}{Program 1:}} \quad &\zevent{push_1}{\Code{L}, 1};\zevent{push_1}{\Code{H}, 0};\eff{store} \quad \text{\textcolor{gray}{and}} \quad\text{\textcolor{gray}{Program 2:}} \quad \zevent{push_2}{\Code{L}, 1};\zevent{push_2}{\Code{H}, 1};\eff{store} 
  \\\text{\textcolor{gray}{Memory 1:}} \quad & [(\Code{L}, 0); (\Code{L}, 0)] \Downarrow \textcolor{red}{[(\Code{L}, 1), (\Code{L}, 0)]} \quad\quad\quad\text{\textcolor{gray}{Memory 2:}} \quad [(\Code{L}, 0); (\Code{L}, 0)] \Downarrow \textcolor{red}{[(\Code{L}, 0), (\Code{L}, 1)]} 
\end{flalign*}\noindent
Here, $\Code{L}$ and $\Code{H}$ are the low (public) and high (secret)
security levels, with $\Code{L} \sqsubseteq \Code{H}$.  To ensure
indistinguishability, public commands (level $\Code{L}$) must use
identical argument values in both programs, whereas secret commands
(level $\Code{H}$) may choose different address values ($0$ and $1$).
Since IFC is a property that holds over pairs of executions, the trace
specification $\zevent{push}{\Code{L}, \langle 1,1\rangle}$ identifies
two programs performing a $\eff{push}$ operation with the same
security label ($\Code{L}$) and value (1); in contrast,
$\zevent{push}{\Code{H}, \langle 0, 1\rangle}$ captures a $\eff{push}$
operation with security label $\Code{H}$ that pushes value 0 in one
execution and 1 in the other.  Although both executions start from the
same initial memory state ([{(\Code{L}, 0), (\Code{L}, 0)}]), the IFC
machine may yield different final states ([{(\Code{L}, 0), (\Code{L},
    1)}] and [{(\Code{L}, 1), (\Code{L}, 0)}]) after performing the
$\eff{store}$ which uses the $\Code{H}$ secret pointer (either 0 or 1)
to store the $\Code{L}$ value (1).  The goal of a PBT generator is to
generate input sequences like these to determine if an IFC machine
implementation will fault prior to the $\eff{store}$ being executed.

To avoid generating invalid or uninteresting test programs that
violate non-interference (e.g., 
$\zevent{push}{\Code{L}, \langle 0, 1 \rangle}$),
operate over invalid addresses (e.g.,
$\zevent{push}{\Code{L},\langle -1, -1\rangle}$), or
construct executions with uninteresting secrets
(e.g., $\zevent{push}{\Code{H}, \langle 1, 1\rangle}$,
we employ the following \tyName{} specifications to guide generation:
\begin{align*}
  &\effLR{\allA}\; \eff{push}\; \I{lvl}\;\langle x,\;y\rangle\; \effLR{\msg{push}{\I{lvl} = \Code{L} \iff x = y}}
  \\& \effLR{\allA\msgB{push}{\I{lvl}\;x_1\;y_1}(\anyA \setminus \msgC{store})^* \msgB{push}{\I{lvl}\;x_2\;y_2}{\I{isAddr}(x_2) \land \I{isAddr}(y_2)}}\;  \eff{store} \; \effLR{\eff{store}}
\end{align*}\noindent  
The post-condition trace for $\eff{push}$ enforces that its arguments
must only be equal if they are intended to be public, while the
pre-condition trace of a $\eff{store}$ event requires that the stack
contain at least two elements (i.e., there be at least two
$\eff{push}$ operations with no intervening $\eff{store}$), with the
top element of the stack referencing the memory location to be
updated.

\begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
  let push_gen () =
    let (x: int) = assume (isArr x) in
    let (y: int) = assume (isArr y) in
    (assume (x = y); ?$\eff{push}$? L ?$\langle \Code{x, y}\rangle$?) ?$\oplus$? (assume (x != y); ?$\eff{push}$? H ?$\langle \Code{x, y}\rangle$?)
  in push_gen (); push_gen (); ?$\eff{store}$?;
\end{minted}

\end{example}

\begin{example}[De Bruijn Index]\label{ex:de-bruijn-index}
  We consider how to apply our approach to the
  well-studied~\cite{BeginnerLuck,ZMD+23,FQL24} problem of testing the
  correctness of an interpreter for simply-typed lambda calculus
  (STLC) terms. Unlike these earlier efforts, we consider terms in
  which variables are represented by their de Brujin
  index~\cite{DeBruijn} and seek to use PBT to discover errors in an
  interpreter implementation that fails to correctly increment the
  index during substitution under a lambda abstraction, leading to
  incorrect variable capture.
  \begin{align*}
    \text{\textsc{Reduction rule}:} \quad & (\lambda t. e)\; v \hookrightarrow e [0 \mapsto v]\\
    \text{\textsc{Incorrect substitution}:} \quad & (\lambda t. e)[n \mapsto v] = \lambda t. (e[\textcolor{red}{n} \mapsto v]) \quad \textcolor{red}{\xmark} \text{ \textcolor{gray}{should be $n + 1$}}
  \end{align*}\noindent
  The following well-typed STLC term can trigger a substitution error in
  an implementation that incorrectly implements substitution as shown above:
  \begin{flalign*}
    & (\lambda \Int. (\lambda (\Int\sarr\Int). [0]\;[1])\; (\lambda \Int. [0]))\; 3 && \tag{$e_\Code{STLC}$}\label{ex:e4} \\
    &\hookrightarrow (\lambda (\Int\sarr\Int). \textcolor{red}{3}\;[1])\; (\lambda \Int. \textcolor{red}{3})  \quad &&\text{\textcolor{red}{(wrong substitution ``$[0] \mapsto 3$'')}}
    \\&\hookrightarrow  3\;[1] \quad &&\text{\textcolor{red}{(stuck!)}}
  \end{flalign*}\noindent
  Here, a buggy implementation
  results in the argument value $3$ being mistakenly substituted for the
  bound variable ``$[0]$'' in the two inner abstractions, instead of
  ``$[1]$''.

  Guiding test generation for interpreters over \emph{serialized} STLC
  terms is challenging, as the generated token sequences must contain
  \emph{nested function abstractions} with appropriate de Bruijn
  indices; otherwise, errors involving incorrect variable substitution
  with non-zero bound variable indices cannot be detected. Enforcing
  correct de Bruijn indices is particularly difficult in our setting,
  as it requires reasoning about counting properties that are not
  easily expressible using SREs. To increase the expressive power of
  our type langauge, we introduce a \emph{ghost} event
  $\effGray{depth}$ that tracks the current abstraction
  depth\footnote{The well-typedness of STLC terms can also be expressed
    using another auxiliary ghost event $\effGray{ty}$; details are
    provided in the supplementary material. }; as we describe in the
  following sections, ghost events carry a payload whose dependencies
  can still be efficiently tracked and checked using off-the-shelf solvers.
  {\begin{align*}
    \effLR{\Code{LAST}(\msgAGray{depth}{d}) \msgA{token}{\boxed{(\lambda t.}\;} \msgAGray{depth}{d + 1} \allA }\; \eff{token}\;\boxed{)}\;\effLR{\msgA{token}{\boxed{)}\;} \msgAGray{depth}{d}}
  \end{align*}}\noindent
  As shown above, upon entering a function abstraction, we retrieve
  the last tagged depth (assumed to be initialized to $0$), increment it at the
  start of the body, and restore it upon exiting. Leveraging
  $\effGray{depth}$, we can specify a correct de Bruijn index 
  constraint as follows:
  \begin{align*}
    \effLR{\Code{LAST}(\msgBGray{depth}{d}{n < d})}\; \eff{token}\;\boxed{[n]}\;\effLR{\msgA{token}{\boxed{[n]}\;}}
  \end{align*}\noindent
  Here, the bound variable index $n$ is required to be less than the
  current depth $d$. The following code snippet shows a test generator
  for nested abstractions that adheres to this constraint:
  % \begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
  %   let rec abs_gen (d: depth) =
  %     (let (i: int) = assume (0 <= i && i < d) in ?$\eff{token}\; \boxed{[i]}$?) ?$\oplus$?
  %     (let t = random_stlc_ty () in ?$\eff{token}\;\boxed{(\lambda t. [0]};$? abs_gen (d + 1); ?$\eff{token}\;\boxed{)\;(\lambda t. [0])}$?
  % \end{minted}
  \begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
    let rec abs_gen (d: depth) =
      (let (i: int) = assume (0 <= i && i < d) in ?$\eff{token}\; \boxed{[i]}$?) ?$\oplus$?
      (let t = random_stlc_ty () in ?$\eff{token}\;\boxed{(\lambda t.};$? abs_gen (d + 1); ?$\eff{token}\;\boxed{)}$?
  \end{minted}

  \noindent Although the ghost event is not present in the code, it
  serves as a hint to the synthesis procedure to construct a recursive
  function $\Code{abs\_gen}$ parameterized by the current depth $d$,
  ensuring correct tracking of abstraction nesting.
\end{example}

In the following section, we will show how to guide a synthesizer to
only generate traces consistent with \tyName{}-based specifications.
We emphasize that because these specifications are used primarily to
constrain the search space of terms used to synthesis a test
generator, they give developers significant leeway on the level of
precision captured: less precise underapproximations simply lead to
potentially less effective generators.
