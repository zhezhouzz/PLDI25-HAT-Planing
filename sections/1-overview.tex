\section{Overview}
\label{sec:overview}

To motivate our approach, consider how we might test the (highly
simplified) model of a distributed database application depicted in
\autoref{fig:database}.

\begin{figure}[t!]
    \centering
    \includegraphics[width=0.75\linewidth]{figures/Controller-Database.drawio.png}
    \caption{A simplified database access workflow.}
    \label{fig:database}
\end{figure}

This system includes two components: a user that issues read and write
messages to a model of a database under test, and a database component
responsible for persisting user-supplied writes, and responding to
user requests to read its contents.  To simplify this example, we
assume the database manages a single integer-valued record that users
can read and write.  As with the earlier key-value store, messages are
asynchronous and separated into two categories, one for requests and
another for the corresponding responses.  Each response carries a
status flag indicating if the request was successful.  A \textsf{true}
status value on a $\eff{writeRsp}$ message indicates that the
corresponding request was successfully persisted to the database,
while a \textsf{true} status flag on a $\eff{readRsp}$ message
indicates that the database is not empty, and the integer in its
payload corresponds to a previously written value.

Since our focus is on deriving a controller that schedules messages
and determines payloads to drive a testing procedure, we are
unconcerned with the implementation of the database --- our primary
interest is in the specification of its interface and the dependencies
that must hold on messages sent between the users and the database,
since these are the primary elements that inform scheduling decisions.
Our goal is to synthesize a controller that generates user requests
and orders the delivery of messages between the user and the database
in a way that drives executions towards a violation of a desired
safety property.

In the figure, the $\eff{readReq}$ and $\eff{writeReq}$ messages sent
by the user are independent of any prior messages and any actions
taken by other components, and can then thus be freely created and
sent by a controller. We refer to such messages as
\emph{generable}. In contrast, messages sent from the database back to
to the user are can only be produced in response to other message. As
the controller can only indirectly trigger such messages, we refer to
them as \emph{observable}.

\paragraph{Traces and safety}
In response to user inputs, an executable model generates a sequence
of messages with concrete values as payloads, which we refer to as a
\emph{trace}.  For our running example, we assume a user expects the
database to satisfy a \emph{read-your-writes} (RYW) policy~\cite{...}
in which reads should see the most recent write to the database.
Under a database that provides EC semantics, however, users might
witness the following trace: %
{\small
  \begin{align}
    &\effGreen{writeReq(3)};\effBlue{writeReq(4)};\effBlue{writeRsp(4,\true)};\effRed{readReq};\effGreen{writeRsp(3,\true)};\effRed{readRsp(4,\true)}
      \label{eqn:traceEx}\tag{$tr_1$}
  \end{align}}
\noindent In this trace, the $\effRed{readRsp}$ message is generated
in response to a previously issued $\eff{readReq}$, but returns a
value other than the most recently written one.  This can happen, for
example, when messages on $\eff{writeReq}$ events are not guaranteed
to be serviced in-order, or when the database state is replicated and
the effect of the $\effGreen{writeRsp(3,true)}$ event has not been
propagated to the replica that responds to the $\effRed{readReq}$
message.

The following symbolic LTL$_f$ formula~\cite{...}: formally captures a
violation of RYW: %
{\footnotesize
  \begin{align} \finalA (\msg{writeRsp}{v = \Code{x} \land st = \true}
    \land \nextA (\neg \msg{writeRsp}{st = \true} \untilA
    \msg{readRsp}{v = \Code{y} \land st = \true \land \Code{y} \not=
      \Code{x}})
    \label{eqn:autoEx}\tag{$\negSCA$}
  \end{align}} %
\noindent
Here, $\msg{writeRsp}{v = \Code{x} \land st = \true}$ is a predicate
on messages, referred to a \emph{symbolic event}. This predicate
stipulates that this is a succesful $\eff{writeRsp}$ message that
reports the value $\Code{x}$ was written. The formula reads as: "this
trace \emph{eventually} includes a $\eff{writeRsp}$ message reporting
$\Code{x}$ was successfully written; moreover, there are no further
successful writes \emph{until} an $\eff{readRsp}$ message with a
payload $\Code{y}$ different from $\Code{x}$ appears."  This formula
can be translated into a Symbolic Finite Automata (SFA)~\cite{...}, on
which inclusion and emptiness are decidable. It is important to note
that this specification defines an \emph{overapproximation} of
violating traces: not all traces that satisfy this property will be
produced by our database model. For example, although the trace
$\effGreen{writeRsp(3,\true)};\effBlue{readRsp(-1,\true)}$ satisfies
\ref{eqn:autoEx}, it does not correspond to a valid execution of our
model, as it does not contain request messages for either responses.

\paragraph{Controllers}
As mentioned earlier, testing a reactive distributed system requires
the support of a controller that models the environment in which it is
run.  We introduce a DSL for writing such controllers amenable to
automated synthesis. Generating a message in this DSL is analogous to
performing an effect in a functional language, with components playing
a similar role to effect handlers. A controller program manages the
generation of messages, schedules message order, and constrains data
dependencies between messages.  Concretely, to realize the trace
\ref{eqn:traceEx}, the controller must (a) issue user-generable
messages (e.g., $\effGreen{writeReq(3)}$), and (b) ensure that
$\effGreen{writeRsp(3,true)}$ message is allowed to be delivered
before $\effRed{readRsp(4,\true)}$.

A controller program $P_{C}$ that generates traces sufficient to
violate \ref{eqn:autoEx} is shown in \autoref{fig:2pc-term}.  The
program stipulates an ordering on messages which are tagged by the
keywords $\mykw{gen}$ and $\mykw{obs}$ to indicate whether the message
is generated by the user or the database (i.e., the
system-under-test).  The program also provides the payloads for
generable messages, and it binds the payloads of observable messages
to new variables using \lstinline|let|. The constraints on parameters
$\Code{x}$ and $\Code{y}$ are defined by the $\mykw{assert}$
statements on line 1.  Importantly, since the controller does not
control the behavior of internal components, it cannot mandate the
specific values output by the database in response to a
message. Instead, it uses assertions to prune executions that will not
satisfy \ref{eqn:autoEx}. Our synthesis algorithm adds these
assertions to a controller using the specifications of component.
Consequently, assertions may fail; for instance, if the database
component sends a $\eff{writeRsp}$ message with a $\false$ status,
this would violate the assertion on line 4.  Nonetheless, our
synthesis procedure guarantees that it will generate an execution of
the system that produces the expected traces in \ref{eqn:autoEx}, if
one exists.

\subsection{Prophecy Automata Types}

Absent any expectations about component behaviors, we cannot prune
unrealizable traces when searching for executions that violate a
property, e.g.,
$\effGreen{writeRsp(3,\true)};\effBlue{readRsp(-1,\true)}$.  Doing so
requires specifications that constrain every sensible trace in which a
component could be involved; thus, they must be able to capture both
temporal (e.g., response messages should follow corresponding request
messages) and data-dependent (e.g., the payload of a read response
should match the most recent write value) properties. % To be of use,
% They must further align with the actual implementation of system
% under test.
Unlike specifications of a safety violations, which are global
property on traces, e.g., \ref{eqn:autoEx}, crafting a single
s-LTL$_f$ property that captures the set of feasible executions in a
model is non-trivial, as this set is determined by the interactions of
the system's constituent components. Thus, instead of providing a
global specification that characterizes the entire distributed state,
we specify a component's message handlers using \PAT{}s and use these
specifications to compositionally approximate the set of feasible
executions. In our approach, component behaviors are modeled as a set
of function signatures, where a function's name corresponds to the
message it handles, its parameter types define constraints on message
payloads, and its return type uses \PAT{}s to capture relationships
between messages.  Unlike prior work on trace-based types, our
formulation accounts for the asynchronous semantics of these systes,
where handling one message can trigger the sending of new messages
that will only be received later.  Intuitively, this means that the
return type of a handler must include both a ``rely", specifying
assumptions about prior events that allow this type to be manifested,
and a ``guarantee" that constrains future events. % Based on this
% intuition, we introduce Prophecy Automata Types (\PAT), which
% provide constraints on traces that regulate the kind and content of
% messages that are received after the handler returns.

\paragraph{History, current, and prophecy automata} The specifications
of the components in our motivating example are shown in
\autoref{fig:spec}. Return types have the form
$\rg{H}{\lastA\msg{M}{\phi}}{F}$, where three components describe the
history, current, and prophecy automata, resp. that establish the
context and effect for any trace containing this message.  Each
signature reads: ``If a message matching $\msg{M}{\phi}$ appears in a
context (trace prefix) accepted by the history automaton $H$, the
future execution (trace suffix) will be accepted by the prophecy
automaton $F$''. Intuitively, prophecy automata are a trace-based
analogue of the prophecy variables\cite{...} used in other state-based
concurrency reasoning approaches to constrain future events. As an
example, the first type in \autoref{fig:spec} characterizes the
behavior of $\eff{writeReq}$ messages. Its history automaton describes
how $\eff{writeReq}$ is handled in an arbitrary context
($\globalA\evparenth{\top}$), and its prophecy automaton guarantees
that a $\eff{writeRsp}$ message will eventually be handled at some
future point, as captured by the $\finalA$ operator.  This
specification captures the asynchronous behavior of request/response
pairs in our example, requiring that the handler of $\eff{writeReq}$
eventually trigger a $\eff{writeRsp}$ message. On the other hand, we
assume little information about the behaviors of the handlers for
$\eff{readRsp}$ and $\eff{writeRsp}$ messages, which is captured by
the prophecy automata of these handlers, which provide no guarantees
about any future messages they may produce ($\allTL$).

\paragraph{Control flow} A handler's \PAT{} can also capture its
relevant control-flow dependencies. For example, the type of
$\eff{readReq}$ uses an intersection type ($\interty$) to encode its
behaviors in the two different contexts under which this message may
be handled, corresponding to whether or not some value has been
previously written to the database. The first \PAT{} specifies that
the handler will eventually respond with the value that was last
requested written, as captured by the history automaton %
{
  $ \finalA \msg{writeReq}{v = \Code{x}} \land
  \neg\nextA\finalA\msg{writeReq}{\top} $ } %
and prophecy automaton %
{ \footnotesize $\msg{readRsp}{v = \Code{x} \land st = \true}$ }.%
Otherwise, no value has been successfully written
($\neg\finalA \msg{writeRsp}{\top}$), and a $\eff{readRsp}$ message
with a $\false$ status will eventually be sent
($\finalA\msg{readRsp}{st = \false}$).

\paragraph{Typechecking} Specifying component behavior in terms of
\PAT{}s, allows us to use a type system to statically check that
controller programs will focus on realizable executions, i.e.,
``Well-typed controller programs do not generate uninteresting
traces''.
%
% In this sense, we can treat $\mykw{gen}$ and $\mykw{obs}$ terms in
% the controller program as as a form of function application that
% should be consistent with the specification of the corresponding
% handler.
%
For example, to type the use of $\eff{readReq}$ on line $5$ in
\autoref{fig:2pc-term}, we first ``divide'' $P_{C}$ into three pieces:
a history (line $1$ - $4$), an action (line $5$), and a future (line
$6$ - $7$). As $P_{C}$ encodes a family of executions, the first
subprogram corresponds to the set of contexts that can occur before
$\eff{readReq}$ is handled, while the last subprogram captures all the
traces that may follow. Thus, we must ensure that each of these pieces
are consistent with the type of $\eff{readReq}$, which requires the
last value written to the database is $\Code{y}$ (line $3$) in the
history, that the message being handled is $\eff{readReq}$, and that a
$\eff{readReq}$ message with value $\Code{y}$ will be produced in the
future (line $7$). Notably, $P_{C}$ can indeed induce a trace that
violates RYW consistency. We can show this by typechecking $P_{C}$
against the \PAT{}
$\rg{\globalA\evparenth{\bot}}{\negSCA}{\globalA\evparenth{\bot}}$. This
\PAT{} asserts that when there are no prior messages,
($\globalA\evparenth{\bot}$), the execution of the controller
generates a trace consistent with \ref{eqn:autoEx}, and no more future
messages are generated ($\globalA\evparenth{\bot}$).

Interpreting message as effects allows us to frame the derivation of a
controller as a component-based synthesis problem, guided by the
\PAT{} specifications of components. \autoref{fig:intuition-algo}
gives a high-level overview of our algorithm, which consists of two
phases. In the first phase, we systematically refine an automaton that
captures violations of our target safety property $A$ to remove traces
that do not correspond to feasible executions. The resulting automaton
$A'$ encodes a stronger property on traces, i.e., $A' \impl A$, which
ensures that each message is consistent with its specification. In the
second phase, we use $A'$ to derive a controller program. As an
example, the set of traces captured by \ref{eqn:autoEx} can be refined
into: %
{\footnotesize
  \begin{align} 
  &\lastA \msg{writeReq}{v = \Code{x}} \seqA 
   \lastA \msg{writeReq}{v =\Code{y} \land v \not=\Code{x}} \seqA \lastA \msg{readReq}{\top} \seqA \\
    &\lastA \msg{writeRsp}{v = \Code{y} \land st = \true} \seqA
    \lastA \msg{writeRsp}{v = \Code{x} \land st = \true} \seqA
    \lastA \msg{readRsp}{v = \Code{y} \land st = \true \land v \not=
    \Code{x}}
    \label{eqn:autoEx2}\tag{$\negSCA'$}
  \end{align}}
\noindent This trace specializes the set of traces captured by the
subformula under the $\finalA$ operator in \ref{eqn:autoEx},
stipulating specific instances of $\eff{writeReq}$ and $\eff{readReq}$
messages. The final two messages in \ref{eqn:autoEx2} align with the
first and last messages in \ref{eqn:autoEx}, ensuring all traces
satisfying \ref{eqn:autoEx2} also satisfy \ref{eqn:autoEx}.  Observe
that the structure of \ref{eqn:autoEx2} closely resembles the
controller program $P_{C}$, with the main difference being that
$P_{C}$ is more operational, dividing messages into $\mykw{gen}$
(generable) and $\mykw{obs}$ (observable) groups. The controller also
provides payloads for $\mykw{gen}$ messages, while payloads in
$\mykw{obs}$ messages are constrained only by local variables.

As previously discussed, the essence of synthesizing a plan program lies in finding the "intersection" of behaviors permitted by both the message specifications $\Delta$ and the reachability property $A$. To operationalize this idea, our algorithm is structured into two main parts. \paragraph{Property Refinement Loop}
The refinement loop is a crucial piece of the algorithm in
\autoref{fig:intuition-algo}, as it ensures that the traces accepted
by the refined formula are consistent with our expectations of
component behaviors. Viewed from another perspective, this algorithm
searches for a family of traces that witness a property violation
until one is found that aligns with provided specifications. A key
challenge is dealing with temporal modalities, like $\finalA$ and
$\untilA$, that permit an arbitrary number of possible messages in the
trace before the messages of interest occur. \ref{eqn:autoEx2}, for
example, includes six events, not all of which appear in
\ref{eqn:autoEx} (e.g., $\eff{readReq}$). While these modalities allow
us to refine the current formula by adding new messages, each of these
messages can impose new requirements that must be satisfied. To
address this challenge, our algorithm lazily injects new messages in
the controller program, and then recursively repairs any unmet
obligations.  As an example, when working on $\eff{readRsp}$ message,
the last message in \ref{eqn:autoEx}, the algorithm identifies that it
must have been issued by the handler for $\eff{readReq}$ (via the
first case of the intersection type in its \PAT{}). Moreover,
$\eff{readReq}$'s type also indicates that the message payload
$\Code{y}$ should belong to a previous $\eff{writeReq}$.  Based on
these constraints, our algorithm refines the current formula by adding
$\eff{writeReq}$ and $\eff{readReq}$ messages before $\eff{readRsp}$,
and marks both as messages whose constraints still need to be
satisfied.
