\section{Overview}\label{sec:overview}


We propose a trace-based specification framework for underapproximating temporal properties in the testing of complex, potentially concurrent systems. Our approach supports the automatic synthesis of test generators, expressed in a domain-specific language, that are provably correct with respect to the given specifications. We first present the key features of our approach, followed by illustrative examples from multiple domains.


\subsection{Trace-based Specifications}

We refer to the sequence of events that comprise a test sequence as a
\emph{trace}.  To reason about dependencies among events in a trace
compositionally, we decompose global trace properties into local
specifications assigned as types to individual operations.  We,
therefore, allow type-level specifications to be associated with each
event in a trace, enabling the specification of complex constraints in
a modular fashion, transferring the burden of event quantification and
data dependency management from a trace-level specification language
to a type system.

Concretely, we model these local specifications as a collection of
operation signatures: parameter types constrain the payloads of
events, while the return type captures relationships between
events. We employ symbolic regular expressions (SREs) to qualify
trace-based properties within a type, following prior work on
trace-based type systems~\cite{KT+14,ZYDJ24,NUKT+18}. However, our
formulation generalizes beyond history-sensitive specifications of
effects or state, allowing types to express latent dependencies among
all events, including those that may occur in the future.

The incorrectness using a triple $[P]\;e\;[Q]$ to represent an underapproximation of program $e$, i.e., for all post states in $Q$, there exists a pre state in $P$ such that the program $e$ can reach the post state from the pre state. We adapt this idea into our trace-based setting as follows:
\begin{align*}
  [\underbrace{\I{presumption}}_{\texttt{state before execution}}]\;\I{code}\;[\underbrace{\I{result}}_{\texttt{state after execution}}]  \;\; \effL\underbrace{\I{history}}_{\texttt{trace before execution}}\effR \;\I{code}\;\effL\underbrace{\I{future}}_{\texttt{new produced trace}} \effR
\end{align*}\noindent
The triple $\effLR{H}\;e\;\effLR{F}$ consists of a history regex $H$, a code $e$, and a future regex $F$. It means ``For all trace $\alpha$ that is matched by future regex $F$, there exists a history trace $\alpha_h$ matched by history regex $H$ such that the trace $\alpha$ can be produced by program $e$ under the history trace $\alpha_h$.''


\subsection{Domain-Specific Language} 

To support test generation across diverse domains, we introduce a domain-specific language (DSL) based on the lambda calculus, extended with recursion, nondeterministic choice ($\oplus$), and (asynchronous) effectful operations ($\eff{op}$). The DSL enables interaction with the SUT through the $\mykw{gen}$ and $\mykw{obs}$ primitives. For example, $\sgen{ReadReq}{}$ asynchronously generates a read request to the SUT, which enable a later on $\zobs{x}{readRsp}{\overline{v}}{e}$ expression to observe the corresponding response, binds it to $x$ in the $\mykw{let}$-body $e$. This approach enables concise expression of interactive test generators for systems such as database transactions and distributed protocols. The DSL further specifies random value generation and property checking via $\mykw{assume}$ and $\mykw{assert}$. Concretely, $\mykw{assume}(\phi)$ constrains $x$ to random values that satisfy the assumption $\phi$, while $\mykw{assert}(\phi)$ terminates the test upon property violation.

\begin{example}[Read Atomicity]\label{ex:read-atomicity}
  Database transactions allow concurrent transactions to operate on
  database state.  To mask latency, client-issued read and write
  operations are typically implemented as asynchronous request and
  response event pairs.  It is desirable that read operations be
  logically atomic, i.e., the response to a client-issued read request
  on a key $k$ always returns the last committed value of $k$ \emph{at
    the time of the request}. The following trace captures an
  execution that violates read atomicity\footnote{For simplicity, we assume
    the database manages a single key that is elided
    from event arguments.}; we also assume that
  every $\eff{writeRsp}$ event is also a commit point: {\small
  \begin{align*}
    &\text{\textcolor{gray}{Client 1:}}  & \zevent{writeReq}{\iota_1,4};\zevent{writeRsp}{\iota_1,4};&
    \\& \text{\textcolor{gray}{Client 2:}} \quad \zevent{readReq}{\iota_2,3};\zevent{readRsp}{\iota_2,3};\zevent{readReq}{\iota_2};& &\textcolor{red}{\zevent{readRsp}{\iota_2,4}}
  \end{align*}}\noindent
  Here, \textcolor{gray}{Client 2} issues two consecutive read
  operations.  A $\eff{readReq}$ event initiates a request to the
  database with transaction id $\iota_2$; the response from the
  database is subsequently observed by a matching $\eff{readRsp}$ that
  follows the request.  In this trace, however, the second response
  witnesses a committed write performed by another
  concurrently-executing, non-committed transaction, with transaction
  id $\iota_1$, that occurs after the request. The following
  trace specification on
  $\eff{readReq}$ events admits executions that satisfy read atomicity:
  \begin{align*}
    &\effLR{\Code{LAST}(\msgA{writeRsp}{\iota\;x})\msgA{readReq}{\iota}\allA}\; \zobs{x}{readRsp}{\iota}{e}\; \effLR{F}
  \end{align*}\noindent
  The regex specifies that if a transaction with id $\iota$ last
  observes that the value of the single key managed by the database is $x$ at the point of $\eff{readReq}$ happening,
  then the response value made by the transaction
  must also be $x$, regardless of any intervening operation.
  \Code{LAST}($\eff{evt}$) is an alias for the following regex:
  \begin{align*}
    \Code{LAST}(\eff{evt})   \equiv \allA; \eff{evt}; (\anyA \setminus \eff{evt})^*
  \end{align*}
  Any trace in which a response to a request yields a different
  value than previously seen by the transaction exposes a
  read atomicity violation. 
  
  Our DSL supports \emph{interactive} test generation through the $\mykw{obs}$ syntax, which enables tests to dynamically observe the effects of the SUT and control subsequent generation behavior. For instance, the following test generator for the read atomicity property utilizes $\mykw{obs}$ to inspect SUT responses:
  \begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
    let rec transaction_gen tid1 tid2 =
      let x = int_gen () in
      ?$\eff{writeReq}$? tid1 x; let _ = ?$\mykw{obs}\;\eff{writeRsp}$? tid1 in
      ?$\eff{readReq}$? tid2; 
      ?$\eff{writeReq}$? tid1 (int_gen ()); let _ = ?$\mykw{obs}\;\eff{writeRsp}$? tid1 in
      let y = ?$\mykw{obs}\;\eff{readRsp}$? tid2 in assert x == y; (() ?$\oplus$? transaction_gen tid1 tid2)
  \end{minted}

  \noindent In each iteration, the generator issues two potentially distinct writes (lines 3 and 5) with a read request in between (line 4), and observes the read result $y$ via $\mykw{obs}$ (line 6). Before generating further transactions, it compares $y$ with $x$ to determine whether to terminate the test exploration and report a violation (i.e., if the read result is different from the first written value).
\end{example}

\begin{example}[Information-Flow Control]\label{ex:ifc} 
We consider test generation for a secure information-flow control (IFC) abstract machine that enforces end-to-end noninterference (EENI)~\cite{pbt-ifc}: if two input programs and initial machine states are indistinguishable to a \emph{public observer}, then the resulting final states must also be indistinguishable. We encode the IFC machine input as a sequence of commands, where each command consists of a pair of arguments representing two syntactically aligned but potentially secret-differing programs.
For instance, the following serialized input corresponds to two indistinguishable IFC programs that both store value $1$ from stack into memory, but at different addresses:
\begin{flalign*}
  &\zevent{push}{\Code{L}, 1, 1};\zevent{push}{\Code{H}, 0, 1};\eff{store} \equiv &  &&
  \\\text{\textcolor{gray}{Program 1:}} \quad &\zevent{push}{\Code{L}, 1};\zevent{push}{\Code{H}, 0};\eff{store} \quad \text{\textcolor{gray}{and}} \quad  &&\text{\textcolor{gray}{Program 2:}} \quad \zevent{push}{\Code{L}, 1};\zevent{push}{\Code{H}, 1};\eff{store} 
  \\\text{\textcolor{gray}{Memory 1:}} \quad & [(\Code{L}, 0); (\Code{L}, 0)] \Downarrow \textcolor{red}{[(\Code{H}, 0); (\Code{L}, 0)]} \quad  &&\text{\textcolor{gray}{Memory 2:}} \quad [(\Code{L}, 0); (\Code{L}, 0)] \Downarrow \textcolor{red}{[(\Code{L}, 0); (\Code{H}, 0)]} 
\end{flalign*}\noindent
Here, $\Code{L}$ and $\Code{H}$ are the low (public) and high (secret) security levels, with $\Code{L} \sqsubseteq \Code{H}$.
To ensure indistinguishability, public commands (level $\Code{L}$) must use identical argument values in both programs, whereas secret commands (level $\Code{H}$) may choose different address values ($0$ and $1$).
Although both executions start from the same initial memory state ([{(\Code{L}, 0); (\Code{L}, 0)}]), the IFC machine may yield different final states ([{(\Code{H}, 0); (\Code{L}, 0)}] and [{(\Code{L}, 0); (\Code{H}, 0)}]) after $\eff{store}$, when it should instead terminate before this command~\cite{pbt-ifc}.

Random generation of such IFC commands often yields invalid or uninteresting cases, e.g., $\zevent{push}{\Code{L}, 1, 0}$ (violates noninterference), $\zevent{push}{\Code{L}, -1, -1};\eff{store}$ (invalid address), or $\zevent{push}{\Code{H}, 1, 1}$ (uninteresting secret).
To avoid these, we employ the following specifications to guide generation:
\begin{align*}
  &\effLR{\anyA}\; \eff{push}\; \I{lvl}\;x\;y; e\; \effLR{\msg{push}{\I{lvl} = \Code{L} \iff x = y} \seqA F}
  \\& \effLR{\allA\msgC{push}(\anyA \setminus \msgC{store})^* \msgB{push}{\I{lvl}\;x\;y}{\I{isAddr}(x) \land \I{isAddr}(y)}}\;  \eff{store}; e \; \effLR{F}
\end{align*}\noindent  
The future regex of $\eff{push}$ enforces that the arguments are equal only at the public level, while the history regex of $\eff{store}$ ensures that the value to store exists (i.e., $\allA\msgC{push}(\anyA \setminus \msgC{store})^*$) and that it is preceded by a $\eff{push}$ with valid addresses. The following code snippet shows a test generator that generates such traces, where $\mykw{assume}\;\phi(x)$ returns an assignment of $x$ that satisfies the given assumption $\phi(x)$.

\begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
  let push_gen () =
    let (x: int) = assume (isArr x) in
    let (y: int) = assume (isArr y) in
    (assume (x = y); ?$\eff{push}$? L x y) ?$\oplus$? (assume (x != y); ?$\eff{push}$? H x y)
  in push_gen x; push_gen y; ?$\eff{store}$?;
\end{minted}

\end{example}

\begin{example}[De Bruijn Index]\label{ex:de-bruijn-index}
  We consider how to apply our approach to the
  well-studied~\cite{BeginnerLuck,CoverageType,FQL24} problem of testing
  the correctness of an interpreter for simply-typed lambda calculus
  (STLC) terms.  We focus on terms in which variables are represented by
  their de Brujin index~\cite{DeBruijn} and seek to use PBT to discover
  errors in an interpreter implementation that fails to correctly
  increment the index during substitution under a lambda abstraction,
  leading to incorrect variable capture.
  \begin{align*}
    \text{\textsc{Reduction rule}:} \quad & (\lambda t. e)\; v \hookrightarrow e [0 \mapsto v]\\
    \text{\textsc{Incorrect substitution}:} \quad & (\lambda t. e)[n \mapsto v] = \lambda t. (e[\textcolor{red}{n} \mapsto v]) \quad \textcolor{red}{\xmark} \text{ \textcolor{gray}{should be $n + 1$}}
  \end{align*}\noindent
  The following well-typed STLC term can trigger the incorrect substitution error:
  \begin{flalign*}
    & (\lambda \Int. (\lambda (\Int\sarr\Int). [0]\;[1])\; (\lambda \Int. [0]))\; 3 && \tag{$e_\Code{STLC}$}\label{ex:e4} \\
    &\hookrightarrow (\lambda (\Int\sarr\Int). \textcolor{red}{3}\;[1])\; (\lambda \Int. \textcolor{red}{3})  \quad &&\text{\textcolor{red}{(wrong substitution ``$[0] \mapsto 3$'')}}
    \\&\hookrightarrow  3\;[1] \quad &&\text{\textcolor{red}{(stuck!)}}
  \end{flalign*}\noindent
  Here, a buggy implementation
  results in the argument value $3$ being mistakenly substituted for the
  bound variable ``$[0]$'' in the two inner abstractions, instead of
  ``$[1]$''.

  Guiding test generation for interpreters over \emph{serialized} STLC terms is challenging, as the generated token sequences must contain \emph{nested function abstractions} with appropriate de Bruijn indices; otherwise, errors involving incorrect variable substitution with non-zero bound variable indices cannot be detected. Enforcing correct de Bruijn indices is particularly difficult, as it requires reasoning about counting properties that are not easily expressible using temporal logic or regular languages. To increase the expressive power of SREs, we introduce a ghost event $\effGray{depth}$ that tracks the current abstraction depth\footnote{The well-typeness of STLC terms can also be expressed using auxiliary ghost events $\effGray{ty}$, the details is shown in supplementary material. }:
  % {\small\begin{align*}
  %   \effLR{\Code{LAST}(\msgAGray{depth}{d}) \msgA{token}{\boxed{(\lambda t.}\;} \msgAGray{depth}{d + 1} \allA \msgA{token}{\boxed{[n]}\;} \allA }\; \eff{token}\;\boxed{)}\;\effLR{\msgA{token}{\boxed{)}\;} \msgAGray{depth}{d}}
  % \end{align*}}\noindent
  {\begin{align*}
    \effLR{\Code{LAST}(\msgAGray{depth}{d}) \msgA{token}{\boxed{(\lambda t.}\;} \msgAGray{depth}{d + 1} \allA }\; \eff{token}\;\boxed{)}\;\effLR{\msgA{token}{\boxed{)}\;} \msgAGray{depth}{d}}
  \end{align*}}\noindent
  As shown above, upon entering a function abstraction, we retrieve the last tagged depth (initialized to $0$), increment it at the start of the body, and restore it upon exiting. Leveraging $\effGray{depth}$, we can enforce the de Bruijn index correctness constraint as follows:
  \begin{align*}
    \effLR{\Code{LAST}(\msgBGray{depth}{d}{n < d})}\; \eff{token}\;\boxed{[n]}\;\effLR{\msgA{token}{\boxed{[n]}\;}}
  \end{align*}\noindent
  Here, the bound variable index $n$ is required to be less than the current depth $d$. The following code snippet shows a test generator for nested abstractions adhering to the de Bruijn index constraint:
  % \begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
  %   let rec abs_gen (d: depth) =
  %     (let (i: int) = assume (0 <= i && i < d) in ?$\eff{token}\; \boxed{[i]}$?) ?$\oplus$?
  %     (let t = random_stlc_ty () in ?$\eff{token}\;\boxed{(\lambda t. [0]};$? abs_gen (d + 1); ?$\eff{token}\;\boxed{)\;(\lambda t. [0])}$?
  % \end{minted}
  \begin{minted}[fontsize = \footnotesize, escapeinside=??, xleftmargin=18pt, linenos]{ocaml}
    let rec abs_gen (d: depth) =
      (let (i: int) = assume (0 <= i && i < d) in ?$\eff{token}\; \boxed{[i]}$?) ?$\oplus$?
      (let t = random_stlc_ty () in ?$\eff{token}\;\boxed{(\lambda t.};$? abs_gen (d + 1); ?$\eff{token}\;\boxed{)}$?
  \end{minted}

  \noindent Although the ghost event is not present in the code, it can be a hint to make our synthesizer to construct a recursive function $\Code{abs\_gen}$ parameterized by the current depth $d$, ensuring correct tracking of abstraction nesting.
\end{example}

In the following section, we will show how to guide a synthesis procedure
to only generate traces consistent with underapproximation specifications.  We
emphasize that these specifications can constrain the search space of terms used to
synthesis a test generator, thus giving developers significant leeway
on the level of precision they enforce on traces.
