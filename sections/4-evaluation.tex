\section{Implementation And Evaluation}\label{sec:impl}

We have implemented a tool based on the above approach, called
\name{}, that targets reactive distributed system models (i.e.,
message-passing systems defined as a collection of actors). \name{}
consists of approximately 14K lines of OCaml code and uses
Z3~\cite{de2008z3} as its backend solver for SMT queries.\footnote{Our
  \techreport{} provides the explanation of all our benchmarks as well as a docker image that contains the source code
  of \name{} and benchmarks.}

\paragraph{Evaluation setting} \name{} takes a safety property in s-LTL$_f$
that is expected to be violated, and handler specifications $\Delta$,
that describe the behavior of messages in terms of \PAT{}s (e.g., the
types shown in \autoref{fig:spec}). The typing context used by \name{}
includes signatures for a number of primitives, including the pure
operators listed in \autoref{fig:term-syntax}.  During synthesis,
\name{} first negates the given property to treat it as a violation
property (e.g., $\negSCA$ in \autoref{sec:overview}), and
systematically explores the space of possible controllers (upto some
fixed time bound) for those that can guide execution to a state
consistent with both $\Delta$ and the violation property. Each
synthesized controller indicates a specific message order and payload
for generated (environment) messages.  \name{} returns an union of
these controller as the final synthesized result.

A synthesized controller is directly executable with an interpreter
implementing the operational semantics in
\autoref{fig:selected-semantics}, where the auxiliary handler
semantics ($\alpha \vDash \zevent{op}{\overline{c}} \Downarrow \beta$)
can be implemented as a random sampler to provide messages $\beta$
that align with handler specifications. However, to evaluate our
approach in a more realistic setting, we adapt our synthesized
controller to run alongside a third-party message handler
implementation.  Specifically, we used handlers implemented in the P
language\cite{DGJ+13,DQ17}, a trace-based, actor-model programming
language tailored for modeling distributed systems and testing
user-defined safety properties.  Similar to our setup, the P runtime
monitors inter-component message traffic, and produces a trace which
it evaluates against safety criteria.  Unlike our method, however, P’s
runtime scheduler explores arbitrary message interleavings randomly
during execution.

To test our synthesized controller with P handlers while also
retaining scheduling control, we compile the controller as a special
component in P that works like a \emph{coordinator}. In this setup,
messages between components are first routed to our controller, where
they are buffered and then forwarded to the actual handlers in
accordance with the order found in the synthesized output.  In other
words, the order in which messages are forwarded from the controller
is determined by the $\mykw{obs}$ statements in the controller
program, allowing it to control the message scheduling.  Additionally,
the coordinator is also responsible for generating messages from
environment components (e.g., a logical user) to the components under
test, again respecting the order in which these messages appear in the
synthesized program.
We compare our synthesized controller with a purely random input message generator for the system under test which uses the default P scheduler to explore all possible message orderings.

Our experimental evaluation addresses three research questions:
\begin{itemize}
\item[\textbf{Q1}:] Is \name{} \emph{expressive}? Can it synthesizes
  controllers for a diverse set of distributed protocols with
  realistic safety properties?
\item[\textbf{Q2}:] Is \name{} \emph{effective}? Do synthesized
  controller programs enable more targeted exploration of the state
  space to witness violations of provided safety properties than
  existing techniques?
\item[\textbf{Q3}:] Is \name{} \emph{efficient}? Is it able to
  synthesize meaningful controller programs in a reasonable amount
  of time?
\end{itemize} %

We have evaluated \name{} on a corpus of complex reactive distributed
system models drawn from a variety of sources (described in the
caption of \autoref{tab:evaluation}) (\textbf{Q1}). We test the
correctness of these models against a number of consistency and safety
properties, including Read-Your-Writes (RYW) consistency introduced in
\autoref{sec:overview}, strong consistency, and unique leader
invariants, among others.  For example, \textsc{RingLeaderElection}
models a leader election algorithm.  Each message transmitted by the
model's actors contain a source ($\I{src}$) and destination
($\I{dest}$), to allow recipient's to distinguish
messages from different nodes. Then, an $\eff{elect}$ handler can
be given the following \PAT{}: {\small\begin{align*}
  &\Code{n}\hasoty{tNode}{\top} \sarr \Code{m}\hasoty{tNode}{\top}
  \sarr \Code{ld}\hasoty{tNode}{v = \Code{m}} \sarr
  \\&\rg{\globalA\evparenth{\top}}{\lastA\msgB{elect}{\I{src}\;\I{dest}\;\I{leader}}{
      \I{src} = \Code{n} \land \I{dest} = \Code{m} \land \I{leader} =
      \Code{m} }}{\finalA\msgB{beLeader}{\I{leader}}{\I{leader} =
      \Code{m}}}
\end{align*}}\noindent
This specification captures a useful property of a leader
election algorithm: when a node $\Code{m}$ receive a message that elects
($\eff{elect}$) itself as leader ($\I{leader} = \Code{m}$) from
another node $\Code{n}$, then node $\Code{m}$ can announce itself to
be the leader ($\eff{beLeader}$).  Details about the reactive
distributed system and safety properties used in our benchmarks are
provided in \techreport{}.

\autoref{tab:evaluation} divides the results of our experiments into
four categories, separated by double bars. The first measures the
complexity of benchmarks with respect to the number of messages
(\#$\eff{op}$) involved and the number of qualifiers used in \PAT{}
specifications and the safety property expressed in s-LTL$_f$.  Our
results show that we are able to specify controller-relevant behavior
using anywhere from $3$ - $17$ different messages, $3$ - $70$ different
kinds of qualifiers (\textbf{Q1}).

The second group of columns describes the size of synthesized
controllers, including the number of variables (\#var), $\mykw{gen}$
messages (\#$\mykw{gen}$), $\mykw{obs}$ messages (\#$\mykw{obs}$), and
assertions (\#$\mykw{assert}$) used in the program. Our synthesized
controllers have anywhere from $1$ - $36$ variables, $5$ - $17$
messages in total, and $1$ - $14$ assertions.  Note that the size of
synthesized program is roughly proportional to the complexity of the
benchmarks (\textbf{Q2}), where the number of qualifiers correlate
with the number of variables and assertions.  As mentioned in
\autoref{sec:synthesis}, our algorithm is biased towards synthesizing
shorter controller program, avoiding synthesizing messages that do not
directly affect the safety property.

The third group of columns reports the performance results of our synthesized controller compared to the random input message generator (\textbf{Q2}). The first column ($\text{violation rate}_{\text{(c,rd)}}$) shows the ratio of violation detection rates between the synthesized controller ($\text{violation rate}_{\Code{c}}$) and the random input message generator ($\text{violation rate}_{\Code{rd}}$) in identifying safety property violations during testing. For benchmarks with deterministic handlers, the synthesized controller achieves a $100\%$ violation rate and does not require multiple runs. Conversely, for benchmarks like \textsc{EspressoMachine}, which simulates a coffee machine that can non-deterministically fail (e.g., due to running out of water or beans), the violation rate is lower. Nevertheless, the synthesized controller achieves at least an 5x to 10000x higher violation rate than the random input message generator, except for the last two benchmarks, where the random generator fails to detect a violation within 10000 attempts. Consequently, the average time for the controller to detect a violation is under $0.1$ seconds across all benchmarks, significantly lower than the average detection time for the random generator ($t_{\text{rd}}$).

The last group of columns in \autoref{tab:evaluation} provides details
on the cost of our synthesis procedure. The first column indicate
total synthesis time (t$_\text{total}$), which takes between $1.13$ to
$60.39$ seconds (\textbf{Q3}); synthesis time is proportional to
benchmark complexity, as reflected in the \#$\eff{op}$ and \#qualifier
columns. 
Notably, the synthesis time is much shorter than the average time required for a random input message generator to detect a safety violation in two-thirds of the benchmarks, particularly in the more complex cases.
The last three columns additionally analyze the behaviors of
\name{} with respect to the number of SAT queries (\#SAT), as well as
the number of forward synthesis (\#fw) and backward synthesis steps
(\#bw) performed by the property refinement loop. Unsurprisingly,
generating more SMT queries (\#SMT) results in longer synthesis times;
the number of these queries directly depends on the number of
iterations of the property refinement loop (i.e., the sum of \#fw and
\#bw).  Oftentimes, the number of forward and backward synthesis steps
exceeds the total number of messages in the controller program because
\name{} may need to backtrack when a wrong type or message
interleaving is selected, which future iterations cannot resolve.

\paragraph{Case study}
We demonstrate that \name{} can be applied to real-world
scenarios, as illustrated in the \textsf{Kermit2PCModel} benchmark,
{\color{red} can we please create a macro for kermit2pc and then call it Anon2PCModel everywhere for double blind and also not using "kermit" internal name.}
which models a two-phase commit (2PC) protocol used by a major cloud
provider. The original P model checks a consistency property for 2PC
transactions, specifically that if there exists a key $\Code{k}$
updated within a transaction $\Code{i}$, any successful read response
to the user should return the latest written value $\Code{x}$ from
that transaction. In our approach, the corresponding violation
property is defined as follows: {\small\begin{align*} \finalA
  (&\msg{updateRsp}{tid = \Code{i} \land key = \Code{k} \land v =
    \Code{x} \land st = \Code{OK}} \land \\&\nextA \neg
  \msg{updateRsp}{tid = \Code{i} \land key = \Code{k} \land st =
    \Code{OK}} \untilA \msg{readRsp}{tid = \Code{i} \land key =
    \Code{k} \land v \not= \Code{x} \land st = \Code{OK}})
\end{align*}}\noindent
where the field $tid$ represents the transaction id, while other
fields have the same meanings as in the example from
\autoref{sec:intro}. This scenario is challenging because the
violation requires observing a successful $\eff{readRsp}$ with an
incorrect value ($v \neq \Code{x}$), the failed $\eff{readRsp}$ won't violate the safety property. The successful response can only occur when the
preceding $\eff{readReq}$ selects a transaction id $\Code{i}$ that maintained by server, where user can send $\eff{startTxnReq}$ to get new transaction id from server with corresponding response ($\eff{startTxnRsq}$).

Without explicitly requesting a new transaction, the random input message generator
has virtually no chance of ``guessing'' a valid transaction
id. However, since the \PAT for $\eff{readReq}$ includes a history
automaton $\finalA \msg{startTxnRsp}{tid = \Code{i}}$, requiring that
the user previously received a valid transaction id $\Code{i}$,
\name{} can synthesize a controller program that strategically
requests a new transaction to trigger the intended violation.


We have evaluated \name{} on a corpus of complex reactive distributed
system models drawn from a variety of sources (described in the
caption of \autoref{tab:evaluation}) (\textbf{Q1}). We test the
correctness of these models against a number of consistency and safety
properties, including Read-Your-Writes (RYW) consistency introduced in
\autoref{sec:overview}, strong consistency, and unique leader
invariants, among others.  For example, \textsc{RingLeaderElection}
models a leader election algorithm.  Each message transmitted by the
model's actors contain a source ($\I{src}$) and destination
($\I{dest}$), to allow recipient's to distinguish
messages from different nodes.
Then, a symbolic event $\msg{elect}{\I{src} = \Code{n} \land \I{dest} = \Code{m} \land \I{leader} = \Code{ld} }$ indicates a node $\Code{n}$ sends node $\Code{m}$ an election message for node $\Code{ld}$ as leader. In the ring leader election algorithm, nodes compare the input elected leader with themselves: if they match, the node announce itself leader; if the elected leader has lower priority, it insists on itself; otherwise, it agrees with the input election message. For an incorrect implementation where receiver nodes never insist on itself as leader, the unique-leader policy may be violated with the following trace:
{\footnotesize
\[
\zevent{wakeup}{\Code{n_1}}; \zevent{wakeup}{\Code{n_2}}; \zevent{elect}{\Code{n_1, n_2, n_1}}; \zevent{elect}{\Code{n_2, n_1, n_2}}; \zevent{elect}{\Code{n_1, n_2, n_2}}; \zevent{elect}{\Code{n_2, n_1, n_1}}; \zevent{leader}{\Code{n_1}}; \zevent{leader}{\Code{n_2}}
\]
}\noindent
which assume there are two nodes ($\Code{n_1}$ and $\Code{n_2}$) in the ring. After waken up (\(\eff{wakeup}\)), they \emph{don't receive message} from each other before after they elects themselves as leader (e.g., $\zevent{elect}{\Code{n_1, n_2, n_1}}$). After receiving each other’s election messages, they both switch to elect each other as leader \emph{simultaneously}, causing each to declare itself as leader (\(\eff{leader}\)), violating the unique-leader policy. Further details on the reactive distributed system and safety properties used in our benchmarks are provided in \techreport{}.
