\section{Introduction}\label{sec:intro}

Testing a model of a distributed system can help to find flaws early
in the development cycle~\cite{BJA+21}.  Frameworks like
P~\cite{DGJ+13,DPQS18}, for example, allow designers to write
executable models whose behaviors can be explored using systematic
testing methods (e.g., bounded model checking).  Models are expressed
in P as (reactive) asynchronously communicating state machines (or
actors) that implement high-level logic, but which abstract away
low-level details that a concrete implementation must address.  Actors
are also responsible for sending and responding to messages from other
actors, or from messages sent by an external environment, i.e., by
users or other actors not under test.  Reasoning over a system's
design thus typically involves (1) providing definitions for the
actors that comprise the model; (2) defining an environment that
closes the system by generating inputs to trigger behaviors; and, (3)
providing a specification that the model should satisfy.

In this setting, the goal of a testing framework is to explore all
possible executions of the closed system derived from (1) and (2) that
can violate (3).  In deciding how to perform this exploration, we must
consider (a) how the actors of the system-under-test (SUT) interact
with the environment and each other (e.g., the messages they generate
in response to other messages), (b) what messages are generated by the
environment, potentially in response to outputs produced by the SUT,
and, (c) the order in which messages generated by actors are received
and handled by others. For example, choosing to control delivery of a
message sent from one actor to another can be used to simulate a weak
consistency semantics~\cite{Session} in a model of replicated state.

A test framework uses a \emph{controller} to answer the last two
questions.  Specifically, the controller consists of both (1) an input
generator that provides input messages to the actors under test, thus
closing the open system and (2) a scheduler that controls the ordering
of messages sent and received by actors in the closed system.
Typically, controllers implement a random or enumerative exploration
stategy.  Although conceptually simple, these approaches make it
problematic to \emph{a priori} determine if the testing framework will
be effective in finding a model-specific design bug, given the
typically very large state space of feasible executions that may have
to be considered. Rather than having the controller undertake
exploration for inputs and message orderings without any foresight on
the property that we seek to violate, this paper investigates an
alternative approach that specializes the actions the controller
performs, explicitly guided by this property.

There are two immediate challenges that need to be overcome to realize
this goal. First, we need to provide specifications expressive enough
to capture interesting kinds of input constraints and message
orderings (i.e., those relevant to the behaviors the model is expected
to exhibit).  Second, we need some way to leverage these
specifications to appropriately bias our search procedure towards
executions that are likely to evince a violation of a desired
behavior. In this paper, we present a unified solution to both these
challenges. The result is a novel framework for testing distributed
system models, driven by a \emph{bespoke} controller expressed as a
program written in a custom DSL tailored for this purpose.  The
controller is \emph{automatically synthesized} from specifications
that define scheduling and external input constraints provided by the
model designer.  A synthesized controller encodes a set of possible
executions that may violate the target property, depending on the
actions of the actors in the SUT. A concrete execution is produced by
iteratively choosing inputs for messages generated by the environment
and observing how the actors in the SUT respond.

To enable controller synthesis, we equip actors with rich
specifications in the form of \emph{prophecy automata types}
(\PAT{}s), a new form of type abstraction that augments refinement
types with automata that describe programs with opaque internal
state~\cite{ZYDJ24}. Our \PAT{}-based specifications serve dual
purposes, describing both (a) how the current global context impacts
how a message is handled, and (b) how executing a message informs
future actions the system can take.

\PAT{} automata are acceptors over LTL$_f$, the language of linear

with efficient decision procedures~\cite{LTLf}, enabling our synthesis
procedure to be highly-automated.

To ground the discussion, consider the specification of a handler for
a $\eff{getReq}(\mathit{k})$ message that queries a key-value store
for the value of a key $\mathit{k}$.  Because of inherent asynchrony
in the way requests and responses are handled, we can expect that
receipt of a $\eff{getReq}$ message by its handler will induce a
$\eff{getResp}(\mathit{k},\mathit{v})$ message from the store at some
arbitrary point in the future; this response message holds the value
$\mathit{v}$ associated with $\mathit{k}$. At a minimum, $\mathit{v}$
should be the same as \emph{some} previously stored value, an
expectation we can encode via the following \PAT:
{ \footnotesize
  \begin{align*}
    % \Code{y{:}int} \garr
    \rg{\underbrace{\finalA \msg{putReq}{k = \Code{key}\land v=\Code{val}}}_\texttt{history automaton}} %
    {\underbrace{\lastA \msg{getReq}{k = \Code{key}}}_\texttt{current automaton}}%
    { \underbrace{\finalA \msg{getRsp}{k = \Code{key} \land v = \Code{val}} }_\texttt{prophecy automaton} }
  \end{align*}
}\noindent This type is parameterized by two variables, $\Code{key}$
and $\Code{val}$, and is comprised of three automata; two of these use
the eventually operator $\finalA$, standard in temporal logics, to
express temporal dependencies between messages. The first automaton
specifies the \emph{history} of messages that occurred prior to the
handling of a $\eff{putReq}$ event. This specification captures any
trace that has stored the value $\Code{val}$ in key $\Code{key}$.  The
second automaton describes the \emph{current} event, captured in this
case as a singleton trace consisting of a $\eff{getReq}$ event over
the key $\Code{key}$ (captured via singleton modality $\lastA$).  The
traces that may follow this event are described by a final
\emph{prophecy} automaton that stipulates that a $\eff{getRsp}$
message whose input contains the key $\Code{key}$ and value
$\Code{val}$ will eventually appear, thus guaranteeing that every
$\eff{getReq}$ message is paired with a $\eff{getRsp}$ message that
returns some written value.  % These constraints enforce an
% atomicity property on reads to the database - even though requests and
% responses may occur far apart in time, reflecting the database's
% asynchronous semantics, the desired behavior specified by this type
% requires all correct executions to be strongly consistent.

Intuitively, this type only ensures eventually consistent (EC)
guarantees~\cite{Burckhardt2014,Session}, since the store is free to
buffer and respond to read and write requests arbitrarily. While
performant, this policy can be too permissive for users, who may want
a strongly consistent (SC) store, i.e., one that always returns the
value of a key at the point their request message is handled.  We can
specify this safety property as the following LTL$_f$
formula:\footnote{This specification uses two additional standard
  temporal logic modalities: $\nextA\ \phi$ requires that $\phi$ holds
  at the next step in a trace, and $\phi_1 \untilA \phi_2$ requires
  that $\phi_1$ holds at every following point in a trace until
  $\phi_2$ becomes true.  } { \footnotesize
  \begin{align*}
    \neg (\msg{putReq}{k = \Code{key} \land v = \Code{val}} \land \nextA (\neg \msg{putReq}{k = \Code{key}} \untilA \msg{getRsp}{k = \Code{key} \land v \not= \Code{val}}))
  \end{align*}
}\noindent Observe that probing if a store is SC cannot be done by
testing how messages are handled in isolation, as a violation of SC
crucially depends on a specific sequence of get and put messages with
appropriate inputs.  The above specification identifies an erroneous
execution as one whose last $\eff{putReq}$ binds $\Code{key}$ to
$\Code{val}$ but in which a $\eff{getRsp}$ message on $\Code{key}$
generated in response to a previously issued $\eff{getReq}$ message
returns a value other than $\Code{val}$.

Our tool, \name{}, generates executions that can test the behavior of
distributed system models by synthesizing a controller program
consistent with the specifications provided for handlers, but which
systematically drives executions to violate a global safety or
liveness property.  These executions differ only in the contents of
messages that are generated from the environment. Each of these
messages subsequenty influences dataflow within the actors that
receive them, and thus the outputs they produce.  We leverage \PAT{}
specifications to implement a top-down, component-based synthesis
algorithm~\cite{tygus,sypet,rbsyn} which constructs a bespoke
controller program that models messages as invocation of events (e.g.,
$\eff{putReq}$).  Traditional top-down synthesizers decompose the
problem by first selecting a candidate component (e.g., a library
method) and recursively synthesizing its arguments, using a
component's specification to constrain the space of candidate
arguments. In our setting, however, the choice of an appropriate
handler depends on both the messages that precede it and the
requirements of the handlers for the messages that follow it.  Our
synthesis algorithm thus uses the data-dependent temporal relations
defined by \PAT{}s to guide the search for a controller program.  This
program denotes a set of possible concrete traces that the SUT is
permitted to generate. Each execution determines a fixed order in
which trigger messages are sent from the environment, and
sent/received by the model's actors.  As it executes, the controller
instantiates concrete values for environment messages, to yield a
concrete schedule.

This paper makes the following contributions:

\begin{enumerate}

\item We formalize a new symbolic trace-based type-guided component
  synthesis algorithm for representing sets of feasible schedules and
  message inputs in open reactive distributed system models.  The
  output of the algorithm is a program written in a DSL tailored for
  expressing test controllers that governs executions in terms of
  message actions among the actors under test and the interaction of
  these actors with an external environment.

\item To guide this algorithm, we propose \PAT{}s, a new type
  abstraction that allows the specification of temporal actions in
  terms of histories and futures over symbolic traces.

\item We formalize a type system based on \PAT{}s and use it to
  justify that synthesized controller programs are consistent with the
  target property being tested.

\item We describe \name{}, a tool that realizes these ideas, and
  present a detailed evaluation that uses a diverse set of
  non-trivial, realistic benchmarks, including a case study drawn from
  an application model developed at a major cloud vendor.  To the best
  of our knowledge, \name{} is the first synthesis procedure capable
  of generating controllers from application-specific handler and
  safety constraints to guide testing of real-world distributed
  models.
