\section{Introduction}\label{sec:intro}

Distributed systems, where participants communicate concurrently via asynchronous message-passing, are challenging to reason about. 
Reactive systems have become a popular abstract model for distributed systems. They consist of \emph{components} that communicate with each other and the \emph{environment} by sending and receiving messages. Sent but unreceived messages can be arbitrarily rescheduled by the environment, simulating realistic network transmission.
Sent but unreceived messages can be arbitrarily rescheduled by the environment, simulating realistic network behavior. Messages generated and sent during the execution of a reactive system can be arranged into traces, which are sequences of messages ordered by their actual time of receipt.
Unlike the traditional state-based approach, which relates input and output states, reactive systems adopt a trace-based view \cite{OldSurveyOfReactiveSystem}, where properties are expressed using \emph{temporal logic} to constrain the order of messages within a trace \footnote{In a effect point of view, the \emph{messages} can be treated as \emph{events}, where components that waits for incoming messages can be treated as a set of effect handlers. We will not distinguish messages and events in the rest of the paper.}.

To illustrate a reactive system concretely, consider a server implementing a simplified two-phase commit (2PC) protocol, as depicted in \autoref{fig:2pc-workflow}. This reactive system includes three types of components: the user, coordinator, and database. The server's 2PC implementation involves only the coordinator and database components, while the user (shown within a dashed square) is considered part of the environment. In this distributed system, data is stored in the database component, but the user cannot access it directly. Instead, the user interacts with the coordinator, which serves as an intermediary, forwarding and processing read and write requests (e.g., messages ending in $\eff{Req}$ and $\eff{Rsp}$ in \autoref{fig:2pc-workflow}).
For clarity, we use $\eff{read/write}$ to represent messages between users and coordinators, and $\eff{get/put}$ for messages between coordinators and the database. Additionally, the coordinator can send either a $\eff{commit}$ or $\eff{abort}$ message to the database to finalize or cancel data modifications. These messages contain a payload, $va$, indicating the read or write value, and $st$, indicating the operation's status.
Sent messages are not received immediately; their actual receiving order is determined by the scheduler in environment. The behavior of this reactive system is characterized by the traces it produces. For instance, the strong consistency of the 2PC protocol can be expressed as a temporal property: all $\eff{readRsp}$ messages must return the most recent successful write value (i.e., the payload of a $\eff{writeRsp}$ message with a $\true$ status).

However, the advantages of modeling message-passing communication in distributed systems with reactive systems come at a cost: these systems are inherently challenging to reason about due to their intrinsic complexity. One major source of complexity is their highly non-deterministic nature -- every possible message interleaving during execution must be accounted for by the scheduler. Scheduling is critical, as many concurrency bugs arise from specific message orders.
Moreover, properties in realistic reactive systems often involve both temporal and data-dependent relationships. For instance, the strong consistency property introduced earlier not only depends on the receiving order of $\eff{readRsp}$ and $\eff{writeRsp}$ but also requires that they share the same payload. These rich specifications further increase the complexity of reasoning and verifying reactive systems.

In this paper, we focus on a specific form of realizability: identifying a particular scheduling plan for message-passing between components that ensures the observed traces align with a given \emph{realizability property}. For example, we aim to realize a violation of strong consistency in a 2PC server that only guarantees eventual consistency (i.e., read response messages will eventually return the latest write value). This violation occurs when the environment schedules read messages too early, before the latest write value has been finalized.
An example of such a scheduling plan, $P_1$, is illustrated below, where write messages are shown in green and read messages in blue:
{\small\begin{align*}
...;\effGreen{writeReq(x)}; ... \effGreen{writeRsp(x,\true)};...;\effBlue{readReq};...;\effBlue{readRsp(y)}; ... \effGreen{commit(x)};... \quad \text{ where } x \not= y \tag{$P_1$}
\end{align*}}\noindent
As shown above, the strong consistency property is violated because the $\eff{readRsp}$ returns an outdated value $y$, which differs from the most recent write value $x$ (i.e., $\eff{writeRsp(x)}$). This inconsistency relies on two assumptions: one concerning data dependency and the other regarding scheduling order. First, the most recent write value $x$ must be different from the outdated value $y$. Second, at the time $\eff{readReq}$ is received, the $\eff{commit(x)}$ message has not yet been scheduled, preventing the write operation from completing.
On the other hand, the $\eff{commit(x)}$ message will eventually be received, and subsequent reads will return the correct last write value, thereby ensuring eventual consistency.

\OL{Challenges and existing works.}

Finding such a scheduling plan is non-trivial. The search space is vast and unbounded because the input property (e.g., strong consistency), expressed in temporal logic, does not limit the trace length, and every possible message interleaving must be explored. Additionally, to ensure the plan is consistent with the component implementation, both past and future events relative to each message must align with that implementation.
For example, when handling a $ \eff{readReq} $, the system must send a $ \eff{readRsp} $ message (which should occur later) with a payload matching the most recently committed value. This requirement creates a ripple effect—ensuring correctness for one message influences the scheduling of both earlier and subsequent messages, increasing the complexity of the search process.
On the other hand, our scheduling approach is not narrowly focused on a single concrete trace. As demonstrated earlier, we allow for multiple traces that are parameterized by the assignment of values $ x $ and $ y $, providing greater flexibility.

There are two existing classes of approaches. One approach \cite{Verdi} utilizes a rich specification language to precisely express the semantics of component implementation, allowing for the derivation of a scheduling plan with a strong realizability guarantee. However, this method requires significant human effort. 
On the other hand, automated randomized testing \cite{P} for distributed systems does not impose assumptions on the components or additional user efforts, but it also offers no guarantees that such a plan is realizable during testing. We propose introducing a search technique that lies between these two approaches, which remains automated while providing a reasonable realizability guarantee with respect to the given specifications of the components.

\OL{Introduce plan synthesis.}

We treat this problem as a type-based plan synthesis task, where we synthesize an environment that implements a specific scheduling order within a \emph{solver-aided} Domain-Specific Language (DSL) that is consistent with a given \emph{realizability property} (e.g., violation of strong consistency). The semantics of the components are abstracted using refinement types, ensuring that the synthesized program is type-safe.
The program in our DSL defines the receiving order of messages, akin to the scheduling plan $ P_1 $ described earlier. Additionally, we incorporate assertions into our DSL, allowing for multiple plans that are parameterized by any assignments consistent with SMT-solvable qualifiers (e.g., $ x \not= y $). Our DSL also supports non-deterministic choices, enabling the synthesized environment to select from various message orders.
For instance, another valid scheduling plan for the previous example can be:
{\small\begin{align*}
...;\effGreen{writeReq(x)}; ... \effGreen{writeRsp(x)};...;\effBlue{readReq};...; \effGreen{commit(x)};... \effBlue{readRsp(y)}; ... \quad \text{ where } x \not= y \tag{$P_2$}
\end{align*}}\noindent
Note that the $\eff{commit(x)}$ message can be received before $\eff{readRsp(y)}$ since the payload $y$ is determined by the sender of $\eff{readRsp}$ (i.e., the handler of $\eff{readReq}$). Thus, $\eff{commit}$ only needs to occur after $\eff{readReq}$.

Our plan program can be combined with the component implementation and executed with the help of a solver to provide valid assignments in accordance with the assertions. It may also be executed using random sampling. During execution, the components can exhibit any behaviors allowed by their specifications (types), which means that assertions in the plan program may be violated at runtime. However, we guarantee that there exists an execution of the plan program that can produce a trace consistent with the realizability property.

\OL{Solution: Prophecy Automata Type (PAT). }

A key aspect of our synthesis approach is a novel formulation of the asynchronous semantics of message-passing in reactive systems, which facilitates the our synthesis algorithm. Since realizability property of these system represented in data-dependent temporal logic and trace-based view, our formalization should also adopt the same trace-based style.
Our approach is inspired by the recent trace-based refinement type system for effectful programming\cite{HAT}, which can specify the pre-effect context (i.e., the trace before executing an effectful program) and the post-effect context (i.e., the trace after executing an effectful program). These traces are constrained by Symbolic Finite Automata (SFA) and Symbolic Linear Temporal Logic on Finite traces (s-LTL$_f$), which support an automated and decidable decision procedure.
Similarly, we use SFA and symbolic temporal logic, but extending the pre- and post-trace concepts to fit the asynchronous semantics of reactive systems. Unlike synchronous semantics, where the result of an effect operation is returned immediately, in reactive systems, operations like a read are divided into separate requests and responses, such as $\eff{readReq}$ and $\eff{readRsp}$. When the handler of $\eff{readReq}$ receives the request, it cannot directly return the read value; instead, it must package the value into the payload of a $\eff{readRsp}$ message and send it. The timing of when the $\eff{readRsp}$ message is received is not controlled by the component but by the environment, reflecting the non-deterministic nature of message-passing in reactive systems.

Adapting this asynchronous semantics, we introduce Prophecy Automata Type (PAT), which consists of three Symbolic Finite Automata (SFA) that constrain the \emph{history}, \emph{current}, and \emph{prophecy} traces. The prophecy trace predicts the environment’s scheduling and guarantees that certain events will happen in the future. This concept is analogous to prophecy variables\cite{...} in the trace-based view. For example, the type of the $\eff{readReq}$ message can be represented by the following type:
{\small\begin{align*}
    \Code{y{:}int} \garr \rg{\underbrace{\anyA^* \seqA \msgB{commit}{x}{x = \Code{y}} \seqA (\anyA \setminus \msgB{commit}{x}{\true})^*}_\texttt{history automata}}{\underbrace{\msg{readReq}{\true}}_\texttt{current automata}}{ \underbrace{\anyA^* \seqA \msgB{readRsp}{x}{x = \Code{y}} \seqA \anyA^* }_\texttt{prophecy automata} }
\end{align*}}\noindent
The ghost variable $\Code{y{:}int} \garr$ indicates that the type holds for any integer value assigned to $\Code{y}$. We use standard regular expression operators to express the SFA: $\anyA$ represents any arbitrary event, $^*$ denotes the Kleene star, $\seqA$ is concatenation, and $\setminus$ represents set difference. 
The \emph{symbolic event} $\msgB{commit}{x}{x = \Code{y}}$ indicates that the payload (local variable $x$) of the $\eff{commit}$ message is equal to the value $\Code{y}$. This type means that: 
"When the history shows that the last committed value is $\Code{y}$, the handling of the $\eff{readReq}$ message will cause a $\eff{readReq}$ event to happen \emph{now}, and in the \emph{future}, a $\eff{readRsp}$ message with the payload $\Code{y}$ will also be received." 

\OL{Solution: a novel deductive synthesis algorithm. }

With the introduction of PAT, we are able to design a more flexible type-based deductive program synthesis algorithm. When concatenating the three automata in a PAT $\rg{H}{A}{F}$ as $H \seqA A \seqA F$, we essentially obtain a complete summary of the entire execution lifetime. This type allows a program to not only specify the effect context it depends on via the history automata $H$ but also guarantee future behavior through the prophecy automata $F$. This approach fits well with our plan synthesis, which must ensure that each scheduled message is consistent with both past and future events.
Furthermore, with this formalization, our synthesis algorithm can start at any ``middle point'' of the correctness property by slicing it into three parts: history, current, and future (prophecy). This allows the algorithm to easily switch between backward and forward synthesis by shifting the current automata as a "sliding window" along the correctness property. This flexibility ensures that the synthesis is guided by the semantic dependencies of the messages, focusing on specific causal chains.
For instance, our algorithm can prioritize synthesizing $\effGreen{readRsp}$ and $\effGreen{readReq}$ first, even though they are not the first or last messages in plan $P_1$. Additionally, it can concentrate on the causal chain of read operations before write operations, even when they are mixed, as in plan $P_2$. This capability allows the synthesis algorithm smartly search in the large hypothesis space efficiently.

We adopt a type-driven, component-based synthesis algorithm where each event is treated as an invocation of an effect operator (e.g., $\eff{readReq}$). Traditional synthesis involves selecting the next operator and synthesizing its arguments, but this can suffer from a large search space due to arbitrary component ordering. Instead of relying on heuristics, we use the data-dependent temporal relations from the provided HAT to guide the search.
For instance, atomicity assumed by HAT types ensures that every $\eff{readReq}$ must eventually lead to a $\eff{readRsp}$, as we discussed above. Then, even the realizability property $\negSCA$ only includes $\eff{readRsp}$, 
{\footnotesize\begin{align*}
   \anyA^* \seqA \msg{writeRsp}{va = \Code{x} \land stat = \true} \seqA (\anyA \setminus \msg{writeRsp}{stat = \true})^* \seqA \msg{readRsp}{va = \Code{y} \land \Code{y} \not= \Code{x}} \seqA \anyA^* \tag{after desugar into regex}
\end{align*}}\noindent
the corresponding $\eff{readReq}$ must occur first. 
{\footnotesize\begin{align*}
   & \anyA^* \seqA  \msg{readReq}{\top} \seqA \anyA^* \seqA 
   \\&\quad \msg{writeRsp}{va = \Code{x} \land stat = \true} \seqA (\anyA \setminus \msg{writeRsp}{stat = \true})^* \seqA \msg{readRsp}{va = \Code{y} \land \Code{y} \not= \Code{x}} \seqA \anyA^*
\end{align*}}\noindent
Our algorithm, once synthesizing for $\eff{readRsp}$, will smartly list $\eff{readReq}$ as its next subgoals with the help of types of these effect operators.
This approach allows synthesis to start mid-program and synthesize any events required to be happened before or after it. Unlike standard forward or backward synthesis, our algorithm don't need to follow the message order in the expect program, but rather the semantic relations between events.
