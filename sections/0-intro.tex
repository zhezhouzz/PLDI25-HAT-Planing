\section{Introduction}\label{sec:intro}

\OL{Introduce reactive system.}

Reactive systems, which consist of \emph{components} (also referred to as handlers) that consecutively interact with their \emph{environment}, have become a popular programming paradigm for distributed systems. Unlike the traditional state-based approach that treats programs as relations between input and output states, reactive systems adopt a trace-based view \cite{OldSurveyOfReactiveSystem}. A trace is a sequence of observed \emph{messages} (also known as \emph{events}). Components in a reactive system can send and receive messages, while the environment non-deterministically reschedules these messages to simulate arbitrary message interleaving during communication. This message-passing style naturally fits distributed systems and concurrent computation, where multiple participants communicate with each other. In this context, participants can be treated as message handlers that are activated only when a new message is received\footnote{In our setting, \emph{components} and \emph{messages} in the distributed system literature are equivalent to \emph{handlers} and \emph{events} in the effect literature. We will not distinguish between them in the rest of the paper.}.
Moreover, shifting from a state-based to a trace-based view means that the desirable properties of reactive systems are represented using \emph{temporal logic}, which constrains the order of observed events within a trace.

\OL{hard to reasoning: 1) non-determinism 2) data-dependent temporal property.}

However, the benefits of easily modeling message-passing communication in reactive systems come at a cost: they are challenging to reason about with respect to specifications that describe desirable behaviors. One source of complexity stems from the highly non-deterministic nature of these systems -- every possible message interleaving during execution must be considered, since many concurrency bugs arise due to specific message scheduling orders. 
Additionally, the specification of realistic reactive systems (e.g., modern distributed systems) often involves both temporal and data-dependent relationships, further increasing the complexity of reasoning and verification.

\OL{Introduce plan and our problem setting.}

In this paper, we focus on a specific realizability reasoning problem: identifying a particular scheduling plan of message-passing between components that leads the observed traces to be consistent with a given property. 
For example, the strong consistency property in storage system requires that all read response messages return the most recent write value, which is a data-dependent temporal property. However, whether a read result meets this criterion depends on when the environment non-deterministically schedules the read messages to be received. For components that only guarantee eventual consistency (i.e., read response messages will eventually return the last write value), if the environment schedules the read messages too early, the strong consistency property may be violated.
Thus, with a particular scheduling order, the execution of components guaranteeing only eventual consistency can lead to a violation of the strong consistency property. One such scheduling plan $P_1$ is illustrated below, where write messages are represented in green and read messages in blue:
{\small\begin{align*}
...;\effGreen{writeReq(x)}; ... \effGreen{writeRsp(x)};...;\effBlue{readReq};...;\effBlue{readRsp(y)}; ... \effGreen{commit(x)};... \quad \text{ where } x \not= y \tag{$P_1$}
\end{align*}}\noindent
As shown above, the strong consistency property is violated because the $\effBlue{readRsp}$ returns a value $y$ that differs from the most recent write value $x$ (i.e., $\effGreen{writeRsp(x)}$). This occurs because, at the time of the read operation, the write operation has not yet completed (i.e., the final write message $\effGreen{commit(x)}$ has not been scheduled), causing the read operation to return an outdated value. However, the $\effGreen{commit(x)}$ message will be finally received, and the read operation will return the correct last write value, thus ensuring eventual consistency.

\OL{Introduce challenges. }

Finding such scheduling cases is not trivial. The search space is vast and unbounded because the input property (e.g., strong consistency) expressed in temporal logic does not constrain the length of the trace, and every possible message interleaving must be considered. Moreover, to ensure that the scheduling case is consistent with the component implementation, both the past and future events relative to each message must align with the implementation.
For instance, the handler of a $\effBlue{readReq}$ will send a new message $\effBlue{readRsp}$ (expect $\effBlue{readRsp}$ occurs later) with a payload equal to the most recently committed value. This sanity check for one message affects the scheduling of both earlier and subsequent messages, adding further complexity to the search process.
On the other hand, our scheduling case is not over-specialized to a single concrete trace. As illustrated earlier, we allow multiple traces that are parameterized by the assignment of $x$ and $y$.

\OL{Introduce plan synthesis and difference from reactive program synthesis.}

We treat this problem as a type-based plan synthesis task, where we synthesize an environment that implements a specific scheduling order within a \emph{solver-aided} Domain-Specific Language (DSL). The semantics of components are abstracted using refinement types, and the synthesized program is guaranteed to be type-safe.
The program in our DSL defines the sequential \emph{receiving} order of messages, similar to the scheduling plan $P_1$ shown earlier. Additionally, we introduce $\mykw{assume}\; \phi$ and $\mykw{assert}\; \phi$ into our DSL, enabling multiple plans that are parameterized by any assignments consistent with SMT-solvable qualifiers (e.g., $x \not= y$). Our DSL also supports non-deterministic choices, allowing the synthesized environment to choose from multiple message orders.
For instance, another valid scheduling plan for the previous example can be:
{\small\begin{align*}
...;\effGreen{writeReq(x)}; ... \effGreen{writeRsp(x)};...;\effBlue{readReq};...; \effGreen{commit(x)};... \effBlue{readRsp(y)}; ... \quad \text{ where } x \not= y \tag{$P_2$}
\end{align*}}\noindent
Note that the $\effGreen{commit(x)}$ message can be received before $\effBlue{readRsp(y)}$ since the payload $y$ is determined by the sender of $\effBlue{readRsp}$ (i.e., the handler of $\effBlue{readReq}$). Thus, $\effGreen{commit}$ only needs to occur after $\effBlue{readReq}$.

\OL{Introduce difference from reactive program synthesis}

Our environment synthesis and planning problem can be treated as complement of well-known reactive program synthesis problem \cite{ReactiveSynthesis}, which focuses on synthesizing component implementations. The key distinction is that, in reactive synthesis, the synthesized components must be correct under \emph{every} possible scheduling plan, determined by a total random environment. In contrast, plan synthesis only requires finding \emph{one} scheduling plan that guides the given components to reproduce a desirable trace.
While reactive synthesis defines \emph{what} a desirable component implementation should be, it does not explain \emph{why} or \emph{how} such components achieve the desired behavior. Our approach to plan synthesis offers deeper insights, helping users better understand the complexities of component behavior in modern distributed systems.

\OL{Solution: Prophecy Automata Type (PAT). }

A key aspect of our synthesis approach is a novel formulation of the asynchronous semantics of message-passing in reactive systems, which facilitates the our synthesis algorithm. Since the input property represented in data-dependent temporal logic and trace-based view, our formalization should also adopt the same trace-based style.
Our approach is inspired by the recent trace-based refinement type system for effectful programming\cite{HAT}, which can specify the pre-effect context (i.e., the trace before executing an effectful program) and the post-effect context (i.e., the trace after executing an effectful program). These traces are constrained by Symbolic Finite Automata (SFA) and Symbolic Linear Temporal Logic on Finite traces (s-LTL$_f$), which support an automated and decidable decision procedure.
Similarly, we use SFA and symbolic temporal logic, but extending the pre- and post-trace concepts to fit the asynchronous semantics of reactive systems. Unlike synchronous semantics, where the result of an effect operation is returned immediately, in reactive systems, operations like a read are divided into separate requests and responses, such as $\effBlue{readReq}$ and $\effBlue{readRsp}$. When the handler of $\effBlue{readReq}$ receives the request, it cannot directly return the read value; instead, it must package the value into the payload of a $\effBlue{readRsp}$ message and send it. The timing of when the $\effBlue{readRsp}$ message is received is not controlled by the component but by the environment, reflecting the non-deterministic nature of message-passing in reactive systems.

Adapting this asynchronous semantics, we introduce Prophecy Automata Type (PAT), which consists of three Symbolic Finite Automata (SFA) that constrain the \emph{history}, \emph{current}, and \emph{prophecy} traces. The prophecy trace predicts the environment’s scheduling and guarantees that certain events will happen in the future. This concept is analogous to prophecy variables\cite{...} in the trace-based view. For example, the type of the $\eff{readReq}$ message can be represented by the following type:
{\small\begin{align*}
    \Code{y{:}int} \garr \rg{\underbrace{\anyA^* \seqA \msgB{commit}{x}{x = \Code{y}} \seqA (\anyA \setminus \msgB{commit}{x}{\true})^*}_\texttt{history automata}}{\underbrace{\msg{readReq}{\true}}_\texttt{current automata}}{ \underbrace{\anyA^* \seqA \msgB{readRsp}{x}{x = \Code{y}} \seqA \anyA^* }_\texttt{prophecy automata} }
\end{align*}}\noindent
The ghost variable $\Code{y{:}int} \garr$ indicates that the type holds for any integer value assigned to $\Code{y}$. We use standard regular expression operators to express the SFA: $\anyA$ represents any arbitrary event, $^*$ denotes the Kleene star, $\seqA$ is concatenation, and $\setminus$ represents set difference. 
The \emph{symbolic event} $\msgB{commit}{x}{x = \Code{y}}$ indicates that the payload (local variable $x$) of the $\eff{commit}$ message is equal to the value $\Code{y}$. This type means that: 
"When the history shows that the last committed value is $\Code{y}$, the handling of the $\eff{readReq}$ message will cause a $\eff{readReq}$ event to happen \emph{now}, and in the \emph{future}, a $\eff{readRsp}$ message with the payload $\Code{y}$ will also be received." 

\OL{Solution: a novel deductive synthesis algorithm. }

With the introduction of PAT, we are able to design a more flexible type-based deductive program synthesis algorithm. When concatenating the three automata in a PAT $\rg{H}{A}{F}$ as $H \seqA A \seqA F$, we essentially obtain a complete summary of the entire execution lifetime. This type allows a program to not only specify the effect context it depends on via the history automata $H$ but also guarantee future behavior through the prophecy automata $F$. This approach fits well with our plan synthesis, which must ensure that each scheduled message is consistent with both past and future events.
Furthermore, with this formalization, our synthesis algorithm can start at any ``middle point'' of the correctness property by slicing it into three parts: history, current, and future (prophecy). This allows the algorithm to easily switch between backward and forward synthesis by shifting the current automata as a "sliding window" along the correctness property. This flexibility ensures that the synthesis is guided by the semantic dependencies of the messages, focusing on specific causal chains.
For instance, our algorithm can prioritize synthesizing $\effGreen{readRsp}$ and $\effGreen{readReq}$ first, even though they are not the first or last messages in plan $P_1$. Additionally, it can concentrate on the causal chain of read operations before write operations, even when they are mixed, as in plan $P_2$. This capability allows the synthesis algorithm smartly search in the large hypothesis space efficiently.
