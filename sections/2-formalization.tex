We formalize our approach using a core language, $\DSL$, for
expressing distributed controller programs. This language is a
call-by-value and asynchronous message-passing calculus that abstracts
away details about other processes and their implementation that the
controller interacts with, focussing only on the structure of the
controller program itself. The syntax of $\DSL$ is shown in
\autoref{fig:term-syntax}; it includes both pure and effectful
operations ($\primop$ and $\eff{op}$), non-deterministic choice
($\oplus$), and assertions. Effectful operations correspond to either
\emph{generable} (e.g., $\eff{readReq}$) or \emph{observable} messages
  (e.g., $\eff{readReq}$), which can be decided by an built-in auxiliary predicate $\GEN$.

\paragraph{Operational Semantics} The message-passing semantics of $\DSL$ relies on \emph{message buffers}, which are multi-set of \emph{message} $(\zevent{op}{\overline{c}})$. Evaluating a $\DSL$ program depends
on an input \emph{trace}, i.e., a sequence of effectful operations, and
produces an output trace.  Traces support the standard list operations
(i.e., cons ${::}$ and concatenation $\listconcat{}$).
We define the operational semantics of $\DSL$ as a small-step
reduction relation: $\steptr{\alpha}{(\beta, e)}{~\alpha'}{(\beta', e')}$.
This relation is read as: under the context $\alpha$ and current
message buffer $\beta$, $e$ steps to $e'$, emitting the trace
$\alpha'$ and producing the output buffer $\beta'$. Intuitively, the
context $\alpha$ represents the sequence of messages visible to a
handler, thereby determining its response; the buffers $\beta$ are
sets of messages that have been issued by not yet been made visible to
a handler. The semantics uses an auxiliary judgement,
$\alpha \vDash \zevent{op}{\overline{c}} \Downarrow \beta$, that
describes any new messages that are added to the message buffer as a
consequence of handling a message.

\autoref{fig:selected-semantics} provides the $4$ non-standard rules
of our semantics.\footnote{The remaining rules are completely standard
  and provided in the supplemental material.} The rule for
observable events (\textsc{StObs}) reflects the ``receive-and-send''
behavior of messages produced by handlers. This rule
non-deterministically removes a pending message that matches the
effectful operation ($\eff{op}$), evaluates it under the existing
context, substituting the message payload $\overline{c}$ for arguments
$\overline{x}$ in $e$, the body of the $\eff{let}$ expression. Any new
messages generated as a consequence of handling
$\eff{op}\ \overline{c}$ are added to the resulting message buffer.
The reduction rule for generable events (\textsc{StGen}) is similar;
since these events can be directly performed by the controller, the
rule does not require a corresponding message in the buffer. The \textsc{StAssume} rule applies a substitution $\msubst{x}{c}$ that satifies with qualifier $\phi$ to the body of assume expression; while \textsc{StAssert} rule requires the asserted qualifier to be alreay true ($\top$) after substitution.  

\begin{example}[Operational Semantics]\label{ex:semantics} The first three events in the trace \ref{eqn:traceEx} is
  produced by the controller program \ref{eqn:autoEx} as follows:
  {\footnotesize
    \begin{align*}
      {[]}\vDash{(\emptyset,P_C)}
      &\xhookrightarrow{[]} (\emptyset,\emph{lines $2$ - $7$ of $P_C$, with $x\mapsto 3, y \mapsto 4$}) \tag{\textsc{StAssume}}\\[-0.4em]
      &\xhookrightarrow{[ \zevent{writeReq}{3}]} (\{ \zevent{writeRsp}{3}\},
        \emph{lines $3$ - $7$ of $P_C$}) \tag{\textsc{StGen}}\\[-0.4em]
      &\xhookrightarrow{[\zevent{writeReq}{4}]} (\{\zevent{writeRsp}{3},
        \zevent{writeRsp}{4}\}, \emph{lines $4$ - $7$ of $P_C$}) \tag{\textsc{StGen}}\\[-0.4em]
      &\xhookrightarrow{[\zevent{writeRsp}{4}]} (\{\zevent{writeRsp}{3}\},
        \emph{lines $5$ - $7$ of $P_C$}) \tag{\textsc{StObs}} \\[-0.4em]
      &\xhookrightarrow{[\eff{readReq}]} (\{\zevent{writeRsp}{3}, \zevent{readRsp}{4,\true}\},
        \emph{lines $6$ - $7$ of $P_C$}) \tag{\textsc{StGen}}
    \end{align*}
  }\noindent 
With the help of solver, the first step of reduction performs one possible substitution ($x\mapsto 3, y \mapsto 4$) satisfying the assumption $x\not=y$ (line $1$). In the following two steps, the controller directly generates two $\eff{writeReq}$ messages and adds two $\eff{writeRsp}$ messages

The syntax of $\DSL{}$'s types is shown in \autoref{fig:type-syntax}.
Types include \emph{pure} refinement types, which describe pure
computations, and Prophecy Automata Types (\PAT{}s), which describe
effectful computations.  Pure refinement types are similar to those
found in other refinement type systems~\cite{JV21}, and allow base
types (e.g., {\Code{int}}) to be further constrained by a logical
formula or qualifier. Verification conditions generated by our
type-checker can be encoded as effectively propositional (EPR)
sentences~\cite{Ramsey1987}, which can be efficiently handled by an
off-the-shelf theorem prover such as Z3~\cite{de2008z3}.

\paragraph{Symbolic Finite Automata} Following other recently proposed
trace-based type systems\cite{...}, $\DSL{}$ uses \emph{Symbolic
  Finite Automata} (SFAs)~\cite{Vea13,SFA-minimization,
  SFA-Transducers} to qualify traces, similar to how standard
refinement types use formulae to qualify the types of pure terms.  The
front-end language used to express SFAs is a symbolic version of
\emph{linear temporal logic on finite traces} (LTL$_f$)~\cite{LTLf}.
A \emph{symbolic event} $\msgB{op}{\overline{x}}{\phi}$ is an atomic
predicate that describes a message {$\eff{op}$} whose fields
$\overline{x}$ must satisfy the qualifier $\phi$.\footnote{When the
  field names of a message are clear, we omit the local variables
  $\overline{x}$, e.g., $\msg{writeReq}{v > 0}$ means
  $\msgB{writeReq}{v}{v > 0}$.}  The standard temporal operators
(i.e., test $\evparenth{\phi}$, next $\nextA A$, until $\untilA$) and
various set operators (i.e., complement $\neg$, intersection $\land$,
and union $\lorA$) are defined normally. These operators are
sufficient to express other modalities, e.g., eventually ($\finalA$),
globally ($\globalA$), and importantly, the singleton (last) modality
$\lastA$, which describes a singleton trace which prohibits any
subsequent effects~\cite{LTLf}.% .

\paragraph{Prophecy Automata Types} A \PAT{} $\rg{H}{A}{F}$ is
comprised of three SFAs: a \emph{history} SFA $H$ that captures the
context traces (i.e., a sequence of visible, already handled, symbolic
events) in which a term can be executed, a \emph{current} SFA $A$ that
describes newly handled messages that arise from executing a term, and
a \emph{prophecy} SFA $F$ that characterizes new messages that have
yet to be performed. Function types use \PAT{}s in their result types
to describe the effects they perform, when combined with intersection
types ($\interty$), this allows users to express complex control
flows. Function types also \emph{ghost variables}
($x{:}b \garr \tau$)\cite{...}  to capture data dependencies among
symbolic events; for example, the full signature of the $\eff{getReq}$
handler from \autoref{sec:intro} uses the ghost variables $\Code{key}$
and $\Code{val}$.

A handler type \PAT{} $\rgB{H}{A}{F}{B}$ additional contains a multi-set $B$ of operators $\{\overline{\eff{op}}\}$, which indicts messages $\eff{op}$ in prophecy automata $F$ (i.e., $\eff{getRsp}$ for \PAT of $\eff{getReq}$) are new sent by current handler. To deal with messages that has same name, we assume there is an unique identifier is assigned to these operators (e.g., $\eff{getRsp_1}$, $\eff{getRsp_2}$, ...), which we can successfully decide the location of symbolic event in $F$ by its name in $\bufLR{B}$. When the context is clear, we omit $\bufLR{B}$.

\begin{example}[Strong Consistency] The SC mentioned in \autoref{sec:intro} requires that when the user receive the $\eff{getRsp}$, the gotten value is the same as the put value in current database. A \PAT for $\eff{getReq}$ consistent with SC can be 
{\footnotesize
  \begin{align*}
    \Code{val}\hasnty{tVal} \garr & \Code{key}\hasoty{tKey}{\top} \sarr  \effLR{\finalA \msg{putReq}{k = \Code{key} \land v = \Code{val}} \land \nextA \neg \finalA \msg{putReq}{k = \Code{key}} } %
    \\& \quad \effLR{\lastA \msg{getReq}{k = \Code{key}}}%
    \effLR{(\neg \msg{putReq}{k = \Code{key}}) \untilA \msg{getRsp}{k = \Code{key} \land v = \Code{val}}}\bufLR{ \eff{getRsp} }
\end{align*}}\noindent
whose prophecy automata indicates that there is no no updates ($\eff{putReq}$) happens before the user receives the $\eff{getRsp}$.    
\end{example}


\subsection{Typing rules}

from variables to pure refinement types (i.e., $t$). Type contexts are
not allowed to contain \PAT{}s, as doing so breaks several structural
properties (e.g., weakening) that are used to prove type safety.

\paragraph{Auxiliary typing relations} There are two auxiliary
relations used by our type system: a well-formedness relation
$\Gamma \wellfoundedvdash \tau$ mostly ensures that all qualifiers appearing
in a type $\tau$ are closed under the current typing context $\Gamma$;
and a mostly-standard semantic subtyping relation.
\autoref{fig:selected-typing-rules} highlights two key auxiliary typing rule.
Rule $\textsc{WfHAF}$ additional requires the non-emptiness ($\neg\allTL$ indicates empty automata) of the concatenation of history, current, and prophecy automata in a \PAT. The
inclusion relation over automata $\Gamma \vdash A \subseteq A$ is defined in the next subsection.
Rule $\textsc{SubHAF}$ checks inclusion between the languages of two
$\PAT{}s$ under type context $\Gamma$.  The rule relates history and prophecy
automata contravariantly, while current automata are covariant. The intuition here is that, similar with history automata that provide presumption on previous events for a computation, the prophecy provide presumption on events happens in the future. Thus, both the
history and prophecy automata are the effect assumed by execution.

\paragraph{Observation Capability} The observable message (e.g., $\eff{readRsp}$) cannot just happens by itself, but need another message happens previously (e.g., $\eff{readReq}$) whose handler sent this observable message. Then, this capability of observing a message is capture by a multi-set message name (effect operators), as in handler \PAT. A expression $\zobs{\overline{x}}{op}{e}$ is type-safe only when message name $\eff{op}$ is contained by \emph{observation capability} $B$, where $\eff{op}$ will be consumed during typing on its body $e$.

\paragraph{Controller program typing} Our type rules
have the form $\Gamma ~|~ B \vdash e : \tau$ that reads `` a term $e$ that has type $\tau$ under type context $\Gamma$ and observation capability $B$''. A
subset of our synthesis rules\footnote{The complete set of typing
  rules is included in the \techreport{}.} is shown in
\autoref{fig:selected-typing-rules}, where we elide the well-formedness judgments in the
premises of these rules; which assume all \PAT are well-formed. Rules \textsc{TGen} and \textsc{TObs} are key rules for non-standard $\mykw{gen}$ and $\mykw{obs}$ expression.
Rule \textsc{TGen} first extracts the type of observing effect operator $\eff{op}$ from the typing context with the help of effect operator typing $\textsc{TEOp}$. Besides requiring the arguments ($\overline{v_i}$) is well-typed against parameter types ($\overline{t_i}$) as application rules in standard refinement typing, it additionally requires that the selected handler type $\rg{H}{\lastA\msg{op}{\phi}}{A\seqA F}$ has the same \emph{global} view as the \PAT{} type check against, i.e.:
{\small\begin{align*} \underbrace{ H
  }_\texttt{history}\;\seqA\;\underbrace{
    \lastA \msg{op}{\phi\msubst{x_i}{v_i}} \seqA A }_\texttt{current} \;\seqA\;
  \underbrace{ F }_\texttt{prophecy} \equiv \underbrace{ H
  }_\texttt{history}\;\seqA\;\underbrace{
    \lastA \msg{op}{\phi\msubst{x_i}{v_i}} }_\texttt{current} \;\seqA\;
  \underbrace{ A \seqA F }_\texttt{prophecy}
\end{align*}}\noindent
If this is the case, we move the symbolic event $\msg{op}{\phi\msubst{x_i}{v_i}}$ from the head of the current automata into the tail of the history automata. We also add the sent message $B'$ of \PAT of $\eff{op}$ into observation capability and continue typing on the body expression $e$. Rule \textsc{TObs} is similar, beside the payload of observed $\eff{op}$ is not provided by the controller, thus no need addition typing on parameter types. Moreover, the \textsc{TObs} will consume the observed $\eff{op}$ from observation capability ($\{\eff{op}\} \cup B$). Notably, we can always use the standard subsumption rule
\textsc{TSub} to change the shape of types. The controller should end with an unit value $()$, where rule \textsc{TRet} requires the current automata of its \PAT to a LTL$_f$ formula $\epsTL$, which specifies that automata that only accepts an empty
trace (i.e., $[]$). Finally, the union expression can be typed via rule \textsc{TChoice}, which enable controller to explore different message orderings.


\begin{example}[Controller Typing] We provide
  an informal derivation of typing controller program $P_C$ against a given type
  $\rg{\epsTL}{\negSCA}{\epsTL}$ that encodes the violation of RYR
  policy under type context $\Gamma \doteq \Code{x}\hasoty{int}{\top},
  \Code{y}\hasoty{int}{v \not= x}$. We first apply the subsumption
  rule (\textsc{Tsub}) to convert into its subtype $\rg{\epsTL}{\negSCA'}{\epsTL}$ which is consistent with $P_C$.

      \lastA\msg{writeReq}{v = \Code{x}} }_\texttt{$A_1$} \seqA \underbrace{
      \lastA\msg{writeReq}{v = \Code{y} \land v \not= \Code{x}} \seqA
      \lastA\msg{writeRsp}{v = \Code{y}} \seqA \lastA\msg{readReq}{\top} }_\texttt{$A_2$} \seqA \\&\underbrace{ \lastA\msg{writeRsp}{v = \Code{x}} }_\texttt{$A_3$}
    \seqA \underbrace{ \lastA\msg{readRsp}{v = \Code{y} \land st = \true \land v \not=
        \Code{x}} }_\texttt{$A_4$}

{\footnotesize\begin{align*}
&(\eff{writeReq},  \Code{x}\hasnty{int} \sarr \rgB{\allTL}{\lastA\msg{writeReq}{v = \Code{x}}}{\finalA\msg{writeRsp}{v = \Code{x}}}{\eff{writeRsp}}) \in \Delta
\\&\Gamma \vdash \eff{writeReq}: \Code{x}\hasnty{int} \sarr \rgB{\allTL}{\lastA\msg{writeReq}{v = \Code{x}}}{\finalA\msg{writeRsp}{v = \Code{x}}}{\eff{writeRsp}} \tag{\textsc{TEOp}}
\\&\Gamma \vdash \eff{writeReq}: \Code{x}\hasnty{int} \sarr \effLR{\epsTL}\ \effLR{\lastA\msg{writeReq}{v = \Code{x}}}\ \effLR{A_2 \seqA \lastA\msg{writeRsp}{v = \Code{x} \land st = \true} \seqA A_4} \tag{\textsc{TSub}}
\end{align*}}\noindent
Since the type of $\eff{writeReq}$ is exactly align with the program type $\rg{\epsTL}{A_1\seqA A_2\seqA A_3\seqA A_4}{\epsTL}$, we can continuing type check the rest of program (line $3$ - $7$ of $P_C$) against \PAT $\rg{A_1}{A_2\seqA A_3\seqA A_4}{\epsTL}$.
\end{example}

\subsection{Type Soundness}

\paragraph{Type denotations} Similar to other refinement type systems~\cite{..},
type in $\DSL$ are denoted as their inhabitants (i.e., $\denot{t}$ and $\denot{\tau}$).  The type context $\Gamma$ is denoted as a \emph{substitution} $\sigma$ (e.g., $[x\mapsto 3, y\mapsto 4]$ in \autoref{ex:semantics}) that provides the assignments for binding variables in $\Gamma$.  Moreover, the denotation (accepting language)
of SFAs is the set of traces they can accept. Then,  automata
inclusion under a type context is defined as $\Gamma \vdash A \subseteq
A' \doteq \forall \sigma \in \denot{\Gamma}. \denot{\sigma(A)}

\paragraph{Well-formed Handler specification} A
handler specification should be consistent with the
auxiliary semantics of handlers introduced in
\autoref{fig:selected-semantics}, which defined formally as the following

\begin{definition}[Well-formed handler specification]
  \label{lemma:built-in-typing}
  The handler specification $\Delta$ is well-formed iff for all operator $\eff{op}$ and its type $\overline{x{:}t} \sarr \rgB{H}{\lastA\msgB{op}{\overline{y}}{\phi}}{F}{B}$ in $\Delta$ satisfying
{\small\begin{align*}
    \forall \alpha \in \denot{A}. \forall \overline{c \in \denotation{t}}. \forall \overline{\alpha_i}. \forall \overline{m_i}.\; \alpha_1 \listconcat [m_1] \listconcat ... [m_{n}] \listconcat \alpha_{n+1} \in \denot{F} \impl \alpha \vDash \zevent{op}{\overline{c}} \Downarrow \{m_i\}
\end{align*}}
\end{definition}


\begin{theorem}\label{theorem:fundamental}[Fundamental Theorem] Given
  a well-formed handler specification $\Delta$,
    the trace of effects produced by a well-typed term
    $e$ is captured by its corresponding \PAT $\tau$:
  $\Gamma \vdash e : \tau \implies \forall \sigma, \sigma \in
    \denotation{\Gamma} \impl \sigma(e) \in
    \denotation{\sigma(\tau)}$.\footnote{The proofs of theorems in this section are provided in the \techreport{}.}
\end{theorem}

\begin{theorem}\label{theorem:sound}[Type Soundness] Given
  a well-formed handler specification $\Delta$, with ghost variables $\overline{x{:}b}$ and a violation property $A$, a controller $e$ that satisfies
  $\overline{x{:\rawnuot{b}{\top}}} \vdash e : \rg{\epsTL}{A}{\epsTL}$, then $e$ at least realize one trace consistent with $A$:
 {\small\begin{align*} \exists
    \overline{c{:}b}. \exists \alpha. \msteptr{[]}{(\emptyset,
      e[\overline{x\mapsto c}])}{\alpha}{(\emptyset, ())} \land \alpha \in
    \denot{A[\overline{x\mapsto c}]}
\end{align*}}
\end{theorem}
