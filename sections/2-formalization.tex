To formalize our approach, we first introduce $\DSL$, a Domain-Specific Language (DSL) for controller programs.

\paragraph{Controllers Syntax} Our DSL is a call-by-value and asynchronous first-class calculus with non-deterministic choices ($\oplus$), assertions over first-order qualifiers ($\phi$) over linear arithmetic operations
($\primop$), as well as pure and effectful operators (i.e., message names). Its syntax is shown in \autoref{fig:term-syntax}, which is in a standard A-normal form\cite{?}. The terms in $\DSL$ are syntactically divided into two classes: value $v$ and expression $e$, where the controller are expressed by the latter. $\DSL$ is parameterized over two sets of primitive operators: pure operators (e.g., $>$) include basic arithmetic and logical operators, while effectful operators ($\eff{op}$) indicates \emph{generative} (e.g., $\eff{readReq^{gen}}$) and \emph{observable} messages (e.g., $\eff{readReq^{obs}}$). When context is clear, we omit the superscript of effect operators. The message handling are then simply be effect operator applications in $\DSL$. Precisely, the controller can generate new messages (i.e., $\zgen{op}{\overline{v}}{e}$) to components, and also \emph{observe} messages (i.e., $\zobs{\overline{x}}{op}{e}$) from components and bind corresponding payload to local variables $\overline{x}$.

\paragraph{Operational Semantics} $\DSL$ has a message-passing style asynchronous semantics, which expressed as \emph{traces} that are the sequence of messages. The syntax of traces adopts standard list operations (i.e., cons ${::}$ and concatenation $\listconcat{}$), as shown in
\autoref{fig:selected-semantics}. Traces are lists of
messages $\zevent{op}{\overline{c}}$ that
record the message name $\eff{op}$ and its payloads $\overline{c}$, for example, the traces $tr_1$ that violates RYW policy from \autoref{sec:overview}.

Following standard message-passing semantics, we use \emph{message buffer} $\beta$ (also a trace) to indicates the send but no received messages. The operational semantics of $\DSL$ is then defined via a small-step
reduction relation, $\steptr{\alpha}{(\beta, e)}{~\alpha'}{(\beta', e')}$.
This relation is read as ``under an effect context (i.e., history trace)
$\alpha$, the message buffer $\beta$ and term $e$ reduces to $(\beta', e')$ in one
step and handles (receives) new event $\alpha'$'', where
$\alpha'$ is either empty $\emptr{}$ or holds a single
event. The semantics is parameterized over an auxiliary relation $\alpha \vDash \zevent{op}{\overline{c}} \Downarrow \beta$ that is used to handle the $\zevent{op}{\overline{c}}$ under effect context $\alpha$. The handler of messages doesn't return value synchronously, but put computation results into new messages (i.e., $\beta$), which will be added into message buffer and are expected be received in the future. \autoref{fig:selected-semantics} shows how the corresponding reduction rules describing the asynchronously semantics.\footnote{The remaining rules are completely standard and provided in the \techreport{}.} The reduction rule for observable messages (\textsc{StObs}) capture a ``receive-and-send'' convention. It first non-deterministically choose one sent message $\zevent{op}{\overline{c}}$ with the expected message name from message buffer to receive. Then new sending message ($\beta_3$) that created by handler of this receiving message is indicated by the handler semantics. For result term, we substitutes the local variables $\overline{x}$ with message payload $\overline{c}$ in original term $e$. Also, the message $\zevent{op}{\overline{c}}$ is consumed from message buffer, while new sending message should be added into new message buffer $\buf_1 \listconcat \buf_2 \listconcat \buf_3$. Finally, this reduction handles single message $\zevent{op}{\overline{c}}$. The reduction rule for generatable messages (\textsc{StGen}) is similar, besides the receiving message don't need to be select from message buffer, but directly provided by controller itself. 

\begin{example}[Operational Semantics] The trace $tr_1$ can be evaluated from the controller program $P_C$ introduced in \autoref{fig:2pc-term}, the first three steps are shown as the following

where in the first two steps, the controller directly generates two $\eff{writeReq}$ and leads two $\eff{writeRsp}$ messages in the buffer; while one pending message is consumed from the buffer at the third step.
\end{example}

The syntax of $\DSL$'s refinement types are shown in \autoref{fig:type-syntax}, which uses \emph{pure} refinement types to describe pure computations and Prophecy Automata Types (\PAT{}s) to describe
effectful computations. Our pure refinement types are similar to those
of other refinement type systems~\cite{JV21}, and allow base types
(e.g., {\Code{int}}) to be further constrained by a logical
formula or qualifier (defined in \autoref{fig:term-syntax}). Verification conditions generated by our type-checking algorithm can nonetheless be encoded as effectively propositional (EPR) sentences~\cite{Ramsey1987}, which can be efficiently handled by an off-the-shelf theorem prover such as Z3~\cite{de2008z3}.

\paragraph{Symbolic Finite Automata} Following the recent trace-based refinement types\cite{?}, our type system use \emph{Symbolic Finite Automata} (SFAs)~\cite{Vea13,SFA-minimization, SFA-Transducers} to qualify traces, similar to how standard refinement types use formulae to qualify the types of pure terms. We support two frontend languages expressing SFAs as shown in \autoref{fig:type-syntax}, a symbolic version of \emph{linear temporal logic on finite traces} (LTL$_f$)~\cite{LTLf}, which can additionally desugared into symbolic regular expression (SRE)~\cite{?}. Notably, the \emph{symbolic event} $\msgB{op}{\overline{x}}{\phi}$ is atomic predicate that describes a message {$\eff{op}$} with payloads $\overline{x}$ whose possible assignments are constrained by qualifier $\phi$. When field names of message is clear, we omit the local variables $\overline{x}$, e.g., $\msg{writeReq}{v > 0}$ means $\msgB{writeReq}{v}{v > 0}$.
The temporal modality (i.e., test $\evparenth{\phi}$, next $\nextA A$, until $\untilA$) and set operator (i.e., complement $\neg$, intersection $\land$, and union $\lorA$) are defined normally. It is sufficient to additional express other modality, e.g., eventually ($\finalA$), globally ($\globalA$), and importantly, the singleton (last) modality $\lastA$, which describes a singleton trace. We also use standard regular expression operators in SRE: $\anyA$ represents any arbitrary message, $^*$ denotes the Kleene star, $\seqA$ is concatenation, and $\setminus$ represents set difference.

In addition to the temporal next ($\nextA A$) and until operators
($A \untilA A$), the syntax of HATs includes negation
($\neg A$), intersection ($A \landA A$), union
($A \lorA A$), and concatenation ($A;A$).
\autoref{fig:type-syntax} defines notations for other useful logical
and temporal operators: implication
($A \impl B \doteq \neg A \lor B$), the eventually operator
$\finalA$, the globally operator $\globalA$, and
importantly, the last modality $\lastA$, which describes a
singleton trace, thus prohibiting a trace from including any other
effects~\cite{LTLf}.  \autoref{fig:type-syntax} also provides notations
for specifying the value of an argument {\small
  $\evop{\effop}{{\overline{x}~\sim}{\text{$v_x$}}~\overline{x}}{\phi}$}.

\paragraph{Prophecy Automata Types} Formally, a \PAT $\rg{H}{A}{F}$ contains three SFAs: a \emph{history} SFA $H$ that captures the context traces in which a term can be executed, a \emph{current} SFA $A$ that describes new handled messages after the execution of the term, and a \emph{prophecy} SFA $F$ predicts the new sent bot not received messages. As discussed in \autoref{sec:overview}, we introduce function \PAT ($x{:}t\sarr \tau$) to express types of handlers and intersection type ($\interty$) to express control flows. Moreover, \emph{ghost variables} ($x{:}b \garr \tau$)\cite{?} are introduced to express the data-dependency across symbolic events. For example, the $\Code{x}$ and $\Code{y}$ are (omitted) ghost variables in example type from \autoref{sec:intro}.

\paragraph{Auxiliary typing relations} There are two auxiliary relations used by our type system. The well-formedness relation $\Gamma \wellfoundedvdash \tau$ largely ensure that all the qualifiers appearing in a type $\tau$ are closed under the current typing context $\Gamma$, details rules are provided in our supplemental materials. Our type system also uses a mostly-standard subtyping relation that aligns with the denotation of the types being related.
\autoref{fig:selected-typing-rules} highlights key subtyping rules $\textsc{SubHAF}$ that are over two base \PAT{}s. This rules checks inclusion
between the languages of the automata under type context $\Gamma$, while the history automata are in contravariant, current and prophecy automata are in covariant. The intuition here is that the asynchronous semantics ``delay'' the return result of a computation as message that expected to be received in the future, thus both current and prophecy automata are the effect caused by execution. the include relation over automata $\Gamma \vdash A \subseteq A$ and is defined in the next subsection.

\paragraph{Effect Operator Framing} The types of operator $\eff{op}$ in handler specification can use prophecy automata to predict the things happens in the future which is very powerful, however, this power should be limited to only constrain that new message sent by $\eff{op}$ handler will \emph{eventually} ($\finalA$) be received. The events sent by other handlers is independent from $\eff{op}$ handler, also, the scheduling order is decided by controller instead of handler. Then,  a well-formed handler specification (defined in next subsection) should have prophecy automata in a form $\bigwedge_{i = 1 ... n} \finalA \msg{op_i}{\phi_i}$. In order to allow these type to ``adapt'' the events independently happens in the future, we introduce a framing rule \textsc{TEOpFrame} for operators, where intuitively, we can insert arbitrary automata ($F_1 ... F_{n+1}$) between $\msg{op_i}{\phi_i}$.

\paragraph{Type-guided Deductive Synthesis} Our main set of rules having form $\Gamma \vdash \tau \termsyn e$ establish a type-guided synthesis, which means ``synthesize a term $e$ that has type $\tau$ under type context $\Gamma$''. A subset of our synthesis rules\footnote{The complete set of typing rules is included in the \techreport{}.} is shown
in \autoref{fig:selected-typing-rules}. The synthesis rules are indeed structured over the shape of current automata $A$ in \PAT $\rg{H}{A}{F}$. Recall that our original synthesis judgment is $\rg{\epsilon}{A}{\epsilon}$ (in SRE) wile both history and future automata are empty context. Then, the typing rule consecutively realize symbolic events in $A$ as effect operator applications and move them into history automata. To realize a current automata with first symbolic event be generatable or observable message, we adapt the rule \textsc{TGen} or \textsc{TObs}. For observable message $\eff{op}$ in type $\rg{H}{\msgB{op}{\overline{y}}{\phi} \seqA A}{F}$, the rule \textsc{TObs} select the type of $\eff{op}$. The rule requires the select type $\rg{H}{\msgB{op}{\overline{y}}{\phi}}{A \seqA F}$ has exactly the same global view, i.e.,
{\small\begin{align*}
\underbrace{ H }_\texttt{history}\;\seqA\;\underbrace{ \msgB{op}{\overline{y}}{\phi} \seqA A }_\texttt{current} \;\seqA\; \underbrace{ F }_\texttt{prophecy} \equiv
\underbrace{ H }_\texttt{history}\;\seqA\;\underbrace{ \msgB{op}{\overline{y}}{\phi} }_\texttt{current} \;\seqA\; \underbrace{ A \seqA F }_\texttt{prophecy}
\end{align*}}\noindent
Then we move the event $\eff{op}$ from the head of current automata into tail of history automata and adding the constraint $\overline{y = x}$ to ensure the local payloads $\overline{y}$ are consistent with the parameters $\overline{x}$, then continuing synthesize the rest of program. The rule \textsc{TObs} has the similar manner besides the payload of messages are provided by controller ($\overline{y = v}$), thus we need to enforce both operator type and program type consistent with it. Notably, we can always use the standard subsumption rule \textsc{TSub} to change the shape of types. The synthesis procedure ends with rule \textsc{TEps} when all symbolic events in current automata are synthesized. At last, our deductive synthesis can synthesize different controller and union them together via \textsc{TUnion}, which enable to capture different message orders.

% At last, we would like to highlight a special prophecy strengthening rule for operator type (\textsc{TEOp}) come from the asynchronous semantics. The intuition here is that the asynchronous semantics ``delay'' the return result of a computation as message that has non-zero chance to be received at \emph{any possible step} in the future. The well-formed handler specification $\Delta$ (define in next subsection) always capture all possible situation in the prophecy automata. Then, any automata $F'$ that included by prophecy automata $F$ can leads to another valid operator type.

  \\&\underbrace{ \msg{writeRsp}{v = \Code{y} \land st = \true} }_\texttt{$A_3$} \seqA \underbrace{
  \msg{writeRsp}{v = \Code{x} \land st = \true} \seqA

\end{example}

\subsection{Type Soundness}

\paragraph{Type denotations} Similar with standard refinement type system, our refinement types are detonated ($\denot{...}$) as set of terms that has his type. The type context $\Gamma$ is denoted as a \emph{substitution} $\sigma$ that provides the assignments for binding variables in $\Gamma$. Moreover, the denotation (acceptable language) of SFAs are the set of traces they can accept. Then, the automata inclusion under type context is defined as $\Gamma \vdash A \subseteq A' \doteq \forall \sigma \in \denot{\Gamma}. \denot{\sigma(A)} \subseteq \denot{\sigma(B)}$
% {\small\begin{align*}
%     \Gamma \vdash A \subseteq A' \doteq \forall \sigma \in \denot{\Gamma}. \denot{A} \subseteq \denot{B} 
% \end{align*}}\noindent
The details of these definition can be find in our \techreport{}.

\paragraph{Well-formed Handler specification} As we mentioned, the handler specification should have prophecy automata that only have eventual modality, moreover, its current automata should be singleton ($\lastA$), and also consistent with the auxiliary semantics of handler introduced in \autoref{fig:fig:selected-semantics}. The well-formedness formally defined as the following.

\begin{definition}[Well-formed handler specification]
  \label{lemma:built-in-typing}
  The handler specification $\Delta$ is well-formed
  iff its type in the following shape
{\small\begin{align*}
    \Delta(\eff{op}) ~ = ~ \overline{x{:}t} \sarr \rg{H}{\lastA\msgB{op}{\overline{y}}{\overline{y = x}}}{F \doteq \bigwedge_{i = 1 ... n} \finalA \msg{op_i}{\phi_i}}
\end{align*}}\noindent
Moreover, these types should consistent with the auxiliary semantics of message handler:
{\small\begin{align*}
    \forall \alpha \in \denot{A}. \forall \overline{c \in \denotation{t}}. \alpha \vDash \zevent{op}{\overline{c}} \Downarrow \beta \impl \beta \in \denot{F}
\end{align*}}
\end{definition}

\begin{theorem}\label{theorem:fundamental}[Fundamental Theorem] Given
  a well-formed handler specification $\Delta$,
    the trace of effects produced by a well-typed term
    $e$ are captured by its corresponding \PAT $\tau$: 
  $\Gamma \vdash e : \tau \implies \forall \sigma, \sigma \in
    \denotation{\Gamma} \impl \sigma(e) \in
    \denotation{\sigma(\tau)}$.\footnote{The proofs of theorems in this section are provided in the \techreport{}.}
\end{theorem}

\begin{corollary}\label{theorem:sound}[Type Soundness] Under
  a handler specification that is well-formed, for violation property $A$ with ghost variables $\overline{x{:}b}$, the synthesized controller $e$ that satisfies $\overline{x{:\rawnuot{b}{\top}}} \vdash \rg{\epsilon}{A}{\epsilon} \termsyn e$, the execution trace is produced by $e$ always consistent with by $A$:
  {\small\begin{align*}
    \forall \overline{c{:}b}. \forall \alpha. \msteptr{[]}{([], e[\overline{x\mapsto c}])}{\alpha}{([], ())} \implies \alpha \in \denot{A[\overline{x\mapsto c}]}
\end{align*}}
\end{corollary}
