We formalize our approach using a core language, $\DSL$, for expressing
distributed controller programs.

\paragraph{Controller Syntax} Our language (shown
in \autoref{fig:term-syntax}) is a call-by-value and asynchronous
message-passing calculus that abstracts away details about other
processes and their implementation that the controller interacts with,
focussing only on the structure of the controller program itself.  Its
expression language includes pure operations, non-deterministic choice
($\oplus$), assertions over first-order qualifiers ($\phi$), and
effectful actions over events ($\eff{op}$).  An event can be annotated
as \emph{generative} (e.g., $\eff{readReq^{gen}}$) or
\emph{observable} messages (e.g., $\eff{readReq^{obs}}$); the former
is associated with messages whose payload is determined by the
controller, while the latter is used in messages whose contents are
determined by other handlers.\footnote{We omit the superscript of
  effect operators when clear from context.}.

\paragraph{Operational Semantics} The behavior of a $\DSL$ program
is expressed as \emph{traces}, message sequences over effectful
operations.  The syntax of traces adopts standard list operations
(i.e., cons ${::}$ and concatenation $\listconcat{}$), as shown in
\autoref{fig:selected-semantics}. Traces are lists of messages
$\zevent{op}{\overline{c}}$ that record the message name $\eff{op}$
and its payloads $\overline{c}$.

We define the operational semantics of $\DSL$ in terms of a small-step
reduction relation, $\steptr{\alpha}{(\beta, e)}{~\alpha'}{(\beta',
  e')}$.  This relation is defined in terms of two traces, $\alpha$, a
\emph{context}, that represents the sequence of messages visible to a
handler, against which it can respond to new messages it receives;
and, $\beta$, a \emph{message buffer}, that represents the sequence of
messages that have been issued but not made visible (aka received) by
a handler.  The semantics uses an auxiliary judgement, $\alpha \vDash
\zevent{op}{\overline{c}} \Downarrow \beta$, that is responsible for
injecting new messages into the message buffer in response to handling
a message based on a provided context.

\autoref{fig:selected-semantics} defines two of the rules that define
the semantics\footnote{The remaining rules are completely standard and
  provided in the supplemental material.} The reduction rule for
observable messages (\textsc{StObs}) reflects a ``receive-and-send''
action.  It first non-deterministically chooses a message in the
message buffer that matches an effect operation ($\eff{op}$),
evaluates it under an existing context, substituting the message
payload $\overline{c}$ for arguments $\overline{x}$ in $e$, the body
of the $\eff{let}$ expression, and additionally adds new messages to
the message buffer generated as a result of handling
$\eff{op}\ \overline{c}$.  The reduction rule for generatable messages
(\textsc{StGen}) is similar.  Handling such a message results in a new
sequence of pending messages that are appended to the message buffer;
recall this class of messages is directly emitted by the controller
and thus can be immediately added to the global message buffer.

The syntax of $\DSL$'s type system is shown in
\autoref{fig:type-syntax}.  Types include \emph{pure} refinement types
to describe pure computations and Prophecy Automata Types (\PAT{}s) to
describe effectful computations.  Pure refinement types are similar to
those found in other refinement type systems~\cite{JV21}, and allow
base types (e.g., {\Code{int}}) to be further constrained by a logical
formula or qualifier. Verification conditions generated by our
type-checking algorithm can be encoded as effectively
propositional (EPR) sentences~\cite{Ramsey1987}, which can be
efficiently handled by an off-the-shelf theorem prover such as
Z3~\cite{de2008z3}.

\paragraph{Symbolic Finite Automata} Following recent advances in exploring
the role of trace-based\cite{...}, our type system uses \emph{Symbolic
  Finite Automata} (SFAs)~\cite{Vea13,SFA-minimization,
  SFA-Transducers} to qualify traces, similar to how standard
refinement types use formulae to qualify the types of pure terms.  The
front-end language used to express SFAs is a symbolic version of
\emph{linear temporal logic on finite traces} (LTL$_f$)~\cite{LTLf}.
A \emph{symbolic event} $\msgB{op}{\overline{x}}{\phi}$ is an
atomic predicate that describes a message {$\eff{op}$} with payloads
$\overline{x}$ whose possible assignments are constrained by qualifier
$\phi$.\footnote{When the field names of a message is clear, we omit the local
variables $\overline{x}$, e.g., $\msg{writeReq}{v > 0}$ means
$\msgB{writeReq}{v}{v > 0}$.}   Temporal modality (i.e., test
$\evparenth{\phi}$, next $\nextA A$, until $\untilA$) and various set operators
(i.e., complement $\neg$, intersection $\land$, and union $\lorA$) are
defined normally.  These operators are sufficient to express other
modalities, e.g., eventually ($\finalA$), globally ($\globalA$), and
importantly, the singleton (last) modality $\lastA$, which describes a
singleton trace. 

In addition to the temporal next ($\nextA A$) and until operators ($A
\untilA A$), the syntax of HATs includes negation ($\neg A$),
intersection ($A \landA A$), union ($A \lorA A$), and concatenation
($A;A$).  These operators are sufficient to encode other useful
logical and temporal operators including logical implication,
eventually ($\finalA$), globally ($\globalA$), and last ($\lastA$),
which describes a singleton trace, that prohibits any other
effects~\cite{LTLf}.

\paragraph{Prophecy Automata Types} Formally,
a \PAT $\rg{H}{A}{F}$ is a type composed of three SFAs: a
\emph{history} SFA $H$ that captures the context traces (i.e., a
sequence of visible, already handled, symbolic events) in which a term
can be executed, the \emph{current} SFA $A$ that describes newly
handled messages that arise from the executing an expression, and a
\emph{prophecy} SFA $F$ that characterizes new messages that have yet
to be handled. \PAT{}s can appear in function types to express the
types of handlers, and can be used within intersection types
($\interty$) to express complex control flows. Moreover, \emph{ghost
  variables} ($x{:}b \garr \tau$)\cite{...}  are introduced to express
data dependencies among symbolic events; for example, $\Code{x}$ and
$\Code{y}$ are (omitted) ghost variables in the introductory example
presented in \autoref{sec:intro}.

from variables to pure refinement types (i.e., $t$). Type contexts are
not allowed to contain \PAT{}s, as doing so breaks several structural
properties (e.g., weakening) that are used to prove type safety.

\paragraph{Auxiliary typing relations} There are two auxiliary relations
used by our type system. The well-formedness relation $\Gamma
\wellfoundedvdash \tau$ ensures that all qualifiers appearing in a
type $\tau$ are closed under the current typing context $\Gamma$;
details are provided in the supplemental material. Our type system
also uses a mostly-standard subtyping relation that aligns with the
denotation of the types being related.
\autoref{fig:selected-typing-rules} highlights key subtyping rules.
Rule $\textsc{SubHAF}$ checks inclusion between the languages of two
$\PAT{}s$ under type context $\Gamma$.  The rule relates history
automata contravariantly, while current and prophecy automata are
covariant. The intuition here is that because the asynchronous
semantics \emph{delays} the return result of a computation as a
message that is expected to be received in the future, both the
current and prophecy automata are the effect caused by execution. The
inclusion relation over automata $\Gamma \vdash A \subseteq A$ is
defined in the next subsection.

\paragraph{Effect Operator Framing}  The use of prophecy
automata in specifying handler behavior is very powerful.  However,
since it is a characterization of future events that must happen as a
consequence of executing a handler message, it is important that the
specification does not overly constrain the effects that may be
produced by other handlers that execute independently.  In other
words, a well-formed handler specification (defined in the next
subsection) should have its prophecy automata be in the form
$\bigwedge_{i = 1 ... n} \finalA \msg{op_i}{\phi_i}$.  In order to
allow this type to adapt to independently occuring events in the
future, we introduce a framing rule \textsc{TEOpFrame} for operators
that allows the arbitrary insertion of other automata ($F_1
... F_{n+1}$) between $\msg{op_i}{\phi_i}$.

\paragraph{Type-guided Deductive Synthesis} Our type synthesis rules
have the form $\Gamma \vdash \tau \termsyn e$ that reads ``synthesize
a term $e$ that has type $\tau$ under type context $\Gamma$''. A
subset of our synthesis rules\footnote{The complete set of typing
  rules is included in the \techreport{}.} is shown in
\autoref{fig:selected-typing-rules}. The synthesis rules are
structured over the shape of the current automata $A$ in \PAT
$\rg{H}{A}{F}$.  Rules \textsc{TGen} and \textsc{TObs} describe how synthesis
proceeds for a non-empty current automata.  Consider a message over
a symbolic event $\eff{op}$ that is the head of the trace accepted by
the current automata in a \PAT{}.  Rule \textsc{TObs} first extracts
the type of $\eff{op}$ from the typing context.  It additionally
requires that the selected type $\rg{H}{\msgB{op}{\overline{y}}{\phi}}{A
  \seqA F}$ has the same \emph{global} view as the \PAT{} against which 
synthesis is being performed, i.e.:
{\small\begin{align*} \underbrace{ H
  }_\texttt{history}\;\seqA\;\underbrace{
    \msgB{op}{\overline{y}}{\phi} \seqA A }_\texttt{current} \;\seqA\;
  \underbrace{ F }_\texttt{prophecy} \equiv \underbrace{ H
  }_\texttt{history}\;\seqA\;\underbrace{
    \msgB{op}{\overline{y}}{\phi} }_\texttt{current} \;\seqA\;
  \underbrace{ A \seqA F }_\texttt{prophecy}
\end{align*}}\noindent
If this is the case, we move the event $\eff{op}$ from the head of the
current automata into the tail of the history automata and add the
constraint $\overline{y = x}$ to ensure that the local payload
$\overline{y}$ is consistent with the parameters $\overline{x}$.  We
then proceed with synthesizing the rest of program.  Rule
\textsc{TGen} is similar, excepted for the manner in which the payload
is delivered ($\overline{y = v}$), where $\overline{v}$ is provided by
the controller.  We, therefore, need to ensure that both the operator
type and the program type are consistent with respect to the provided
values.  Notably, we can always use the standard subsumption rule
\textsc{TSub} to change the shape of types. The synthesis procedure
ends with rule \textsc{TEps} when all symbolic events in the current
automata are synthesized; note that the LTL$_f$ formula
$\negA\nextA(\top)$ specifies that automata that only accepts an empty
trace. Finally, our deductive synthesis can synthesize different
controller and union them together via \textsc{TUnion}, which enable
it to explore different message orderings.

\subsection{Type Soundness}

\paragraph{Type denotations} Similar to other refinement type systems~\cite{..},
type denotations in $\DSL$\ ($\denot{...}$) are given as set of terms
that have that type.  The type context $\Gamma$ is denoted as a
\emph{substitution} $\sigma$ that provides the assignments for binding
variables in $\Gamma$.  Moreover, the denotation (accepting language)
of SFAs is the set of traces they can accept. Then,  automata
inclusion under a type context is defined as $\Gamma \vdash A \subseteq
A' \doteq \forall \sigma \in \denot{\Gamma}. \denot{\sigma(A)}
\subseteq \denot{\sigma(B)}$.\footnote{The details of these definition can be find in our \techreport{}.}
% {\small\begin{align*}
%     \Gamma \vdash A \subseteq A' \doteq \forall \sigma \in \denot{\Gamma}. \denot{A} \subseteq \denot{B} 
% \end{align*}}\noindent

\paragraph{Well-formed Handler specification} A
handler specification should have prophecy automata that only express
the eventually modality.  Moreover, its current automata should always
be a singleton ($\lastA$), and should also be consistent with the
auxiliary semantics of handlers introduced in
\autoref{fig:fig:selected-semantics}.  We can state these conditions formally:

\begin{definition}[Well-formed handler specification]
  \label{lemma:built-in-typing}
  The handler specification $\Delta$ is well-formed iff its type in
  the following shape {\small\begin{align*} \Delta(\eff{op}) ~ = ~
    \overline{x{:}t} \sarr
    \rg{H}{\lastA\msgB{op}{\overline{y}}{\overline{y = x}}}{F \doteq
      \bigwedge_{i = 1 ... n} \finalA \msg{op_i}{\phi_i}}
\end{align*}}\noindent
Moreover, these types should consistent with the auxiliary semantics of message handler:
{\small\begin{align*}
    \forall \alpha \in \denot{A}. \forall \overline{c \in \denotation{t}}. \alpha \vDash \zevent{op}{\overline{c}} \Downarrow \beta \impl \beta \in \denot{F}
\end{align*}}
\end{definition}


\begin{theorem}\label{theorem:fundamental}[Fundamental Theorem] Given
  a well-formed handler specification $\Delta$,
    the trace of effects produced by a well-typed term
    $e$ is captured by its corresponding \PAT $\tau$: 
  $\Gamma \vdash e : \tau \implies \forall \sigma, \sigma \in
    \denotation{\Gamma} \impl \sigma(e) \in
    \denotation{\sigma(\tau)}$.\footnote{The proofs of theorems in this section are provided in the \techreport{}.}
\end{theorem}

\begin{corollary}\label{theorem:sound}[Type Soundness] Under
  a handler specification, with ghost variables $\overline{x{:}b}$,
  that is well-formed, and a property $A$ that expresses a violation
  of a safety condition, a synthesized controller $e$ that satisfies
  $\overline{x{:\rawnuot{b}{\top}}} \vdash \rg{\epsilon}{A}{\epsilon}
