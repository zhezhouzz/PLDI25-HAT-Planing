\section{Motivation Example}

\begin{figure}[ht!]
    \centering
    \includegraphics[width=0.75\linewidth]{figures/typed-guided-planing-example.drawio.png}
    \caption{A simple two-phrase commit model.}
    \label{fig:ex-2pc}
\end{figure}

We present a simplified two-phase commit model to motivate our approach, as depicted in \autoref{fig:ex-2pc}. This model comprises three components (machines):
\begin{enumerate} 
    \item The generator simulates user behaviors, enabling the sending and receiving of $\eff{Read/Write}$ messages for reading and writing values (specifically, the field $\Code{v}$ in the payloads). Furthermore, the response message (i.e., messages end with $\eff{Rsp}$) includes a boolean field, $\Code{stat}$, which indicates the status code of the action performed. 
    \item The implementation under test, illustrated in green in \autoref{fig:ex-2pc}, consists of two types of components: the coordinator and the database component. For clarity, we refer to the interactions between the coordinator and the database using $\eff{Put/Get}$ instead of read/write. The actual data is stored within the database components, while the coordinator retrieves this data and determines whether the updated information should be made persistent through $\eff{Commit}$ or $\eff{Abort}$ messages. 
\end{enumerate}


\paragraph{Correctness Property} We aim to establish the correctness property $\exArw$, which signifies strong consistency.\\[-.8em]

$\exArw$: \textit{Any read result (i.e., the $\Code{v}$ field of $\eff{ReadRsp}$) must equal the most recent successfully written value (i.e., when the $\Code{stat}$ field of $\eff{WriteRsp}$ is \Code{true}).}\\[-.8em]

The correctness property $\exArw$ can be formulated as a symbolic LTL (Linear Temporal Logic) formula. However, the implementation may not align with the correctness property $\exArw$. For instance, it may only guarantee eventual consistency; thus, a read result immediately following a successful write might not reflect the written value, as the database may not have yet received the $\eff{Commit}$ message.

\paragraph{Environment and Generator} The environment encompasses all the elements required by the implementation (i.e., the coordinator and database) during execution. This environment is beyond the generator, which only produces the \emph{generated events} (e.g., $\eff{WriteReq}$ and $\eff{ReadReq}$) that need to be handled; it also includes a scheduler that governs the order of message receiving, as well as a monitor that check whether the \emph{observed} events are consistent with the correctness property $\exArw$.

We are particularly interested in identifying an environment program that causes the execution to violate the correctness property $\exArw$. This occurs when a $\eff{ReadReq}$ message is generated but the corresponding $\eff{Commit}$ message has not yet been received by database. An example of such an environment program, denoted as $e$, is provided below. For simplicity, we assume there is only one coordinator and one database, and therefore the source and destination components (machines) of the messages are omitted.

\begin{minted}[xleftmargin=5pt, numbersep=4pt, linenos = true, fontsize = \footnotesize, escapeinside=??]{OCaml}
let (x: int) = ?$\mykw{random}$?(int) in
?$\mykw{assert}$? (x != -1) in
?$\mykw{generate}$? WriteReq x in
(* let (y1: int) = ?$\mykwCmt{observe}$? PutReq in *)
(* ?$\mykwCmt{assert}$? (y1 == x) in *)
(* let (y2: int), (s1: bool) = ?$\mykwCmt{observe}$? PutRsp in *)
(* ?$\mykwCmt{assert}$? (y2 == x && s1 == true) in *)
let (y3: int), (s2: bool) = ?$\mykw{observe}$? WriteRsp in
(* ?$\mykwCmt{assert}$? (y3 == x && s2 == true) in *)
?$\mykw{generate}$? ReadReq in
(* let () = ?$\mykwCmt{observe}$? GetReq in *)
(* let (y4: int) = ?$\mykwCmt{observe}$? GetRsp in *)
(* ?$\mykwCmt{assert}$? (y4 == -1) in *)
(* let () = ?$\mykwCmt{observe}$? Commit in *)
let (y5: int) = ?$\mykw{observe}$? ReadRsp in
(* ?$\mykwCmt{assert}$? (y5 == y4 && y5 != x) in *)
()
\end{minted}
The program $e$ can be considered as three distinct roles: as a generator, a scheduler, and a monitor. Without the commented code, $e$ acts as a generator that can send messages to the coordinator (on lines $3$ and $10$) and receive responses (on lines $10$ and $15$). This behavior is analogous to the following \Code{P} code.

\begin{minted}[xleftmargin=5pt, numbersep=4pt, linenos = true, fontsize = \footnotesize, escapeinside=??]{C}
var x: int;
value = choose(int);
assert(x != -1);
send coordinator, WriteReq, (source = this, v = x);
receive {
    case WriteRsp: ((y3: int, s2: bool)) {}
}
send coordinator, ReadReq, (source = this,);
receive {
    case ReadRsp: ((y5: int,)) {}
}
\end{minted}
In our language of environment program, we distinguish the messages sent by the generator from other messages. The former messages can be ``announced'' using the $\mykw{generate}$ keyword, and it is the environment's responsibility to provide the concrete payload of the message. On the other hand, the environment can $\mykw{observe}$ other messages and store the corresponding payload into variables (e.g., $y_3$ on line $8$).

Moreover, if we include the commented code, the program $e$ will gain a global view (i.e., visibility of all events) and function as a scheduler, dictating the order in which messages are received. For instance, the $\eff{Commit}$ message (line $14$) is received after the $\eff{GetRsp}$ message (line $12$), which is why the read value remains the default value (i.e., $-1$) rather than the value that was successfully written. The assertions in the commented code serve as a monitor to ensure that the execution indeed produce a trace that violates the correctness property $\exArw$.

The underlying intuition is that having a ``global view'' can lead to more effective testing. Therefore, we first synthesize an environment that acts as both a generator and a scheduler. Even if we later ``erase'' the invisible messages (i.e., those not sent or received by the generator), the test remains more efficient.

\paragraph{Axioms and Specification} Due to the asynchronous semantics, the result of a read request is not immediately returned. Therefore, the environment program must understand how one message triggers another. For instance, it recognizes that a read action involves a chain of messages as follows:
\begin{align*}
    \eff{ReadReq} \to \eff{GetReq} \to \eff{GetRsp}(v) \to \eff{ReadRsp}(v)
\end{align*}
\noindent where the payload of both $\eff{GetRsp}$ and $\eff{ReadRsp}$ contains the same value. These relationships were previously referred to as axioms and expressed through multiple symbolic LTL formulas. Now, however, we represent axioms as individual temporal specifications for each message. For example, the specification $\phi_{\eff{ReadReq}}$ defines that when the coordinator handles a $\eff{ReadReq}$, it will send a $\eff{GetReq}$ to the database.

\paragraph{Problem Setting} Our tool takes axioms $\Phi$ and a correctness property $A$ as input, and produces an environment program $e$ as output. We guarantee that running the environment $e$ with any blackbox implementation consistent with $\Phi$ will generate a trace that violates $A$. Furthermore, this environment program $e$ can be transformed into a generator by erasing invisible $\mykw{observe}$ statements and assertions, allowing it to run with the native $\Code{P}$ scheduler and monitor.
